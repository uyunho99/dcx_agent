## 1. 의도 — 사용자가 말한 것과 가정 구분

**사용자가 말한 것**
- 0단계 입력 · 1단계 키워드 발산/수렴 · 2단계 크롤링을 기획안대로 바꾼다. 3단계 이후는 문서가 오면 이어서 한다(D-001).
- 내부 실험용이다. 맥미니 한 대에서 돌리고 저장도 로컬이다. 호스팅하지 않는다(D-002).
- 크롤링 검색어는 1단계 최종 키워드만 쓴다. "에어팟 러닝"이 아니라 "러닝"(D-014).
- 크롤링은 목록을 먼저 다 모으고, 별도 프로세스가 하나씩 들어가 본문을 긁는다(D-033). 목표 100만 건 이상(D-031).
- 개발은 Codex가 한다(D-050). 실행 중 LLM 판단도 Codex로 돌릴 수 있어야 한다. 4단계에서 Jev와 ChatGPT 판정이 함께 나와야 하기 때문이다(D-051).
- LG 에어컨 데이터로 어느 정도 돌아가는지 확인한다(D-040).
- 구체화 · 수정 · 결정의 이유는 모두 기록으로 남긴다.

**Claude의 가정 (틀리면 고쳐 주세요)**
- G1. 기존 세션(옛 입력 형식)은 새 형식으로 변환하지 않는다. 목록에서 "구버전"으로 표시하고 열람만 허용한다.
- G2. 외부 API 키(검색광고 · 데이터랩 · NAVER API HUB · 네이버 쇼핑 · YouTube Data API)는 지금 없다. 키가 없어도 전 과정이 끝까지 돌아야 한다(D-023).
- G3. 1단계 LLM 호출의 기본 백엔드는 지금처럼 Claude API이고, 설정으로 Codex exec로 바꿀 수 있다.
- G4. 한 번의 하네스 실행에서 0~2단계를 모두 끝낸다(4절 대안 A).

**성공의 모습**
LG 에어컨 프로젝트를 새 0단계 폼으로 만들고, R1→R4를 거쳐 3축 키워드를 확정하고, 선택한 채널에서 목록 → 검토 게이트 → 본문 · 댓글 수집을 마쳐 새 스키마 문서가 로컬에 쌓인다. 중간에 프로세스를 죽였다 살려도 이어서 끝난다. 그리고 이 흐름이 네트워크 없이 테스트로도 재현된다.

## 3. 범위

### 0단계 · 입력
1. 0-A 9필드(한줄 정의 · 리서치 질문 · 프로젝트 성격 · 분석 목적 · 핵심 지표 · 사내 제약 · 브랜드 포지셔닝 · 수집 채널 · 이미 아는 것)와 0-B 6필드(제품군 대›중›소 · 연령대 · 성별 · 가구 형태 · 생애주기 · 미래 고객 정의)를 받는다. 제품명 `bk`는 별도 필드로 유지한다(D-013).
2. 프로젝트 성격 · 분석 목적 · 타겟 스코프는 선택 + 보충 서술(D-010).
3. 제품군은 네이버 쇼핑 카테고리 기준으로 자동 제안하고, API가 없으면 LLM이 추정해 "추정"으로 표시한다. 사용자가 고친다(D-015).
4. 입력은 형식과 버전이 있는 `projectContext`로 저장한다. 세션마다 `project_context.md`를 생성한다(D-017).
5. `knownInsights[]`에 0단계 입력분을 `from: "stage0"`으로 저장한다(D-016).

### 1단계 · 키워드
6. R1(5W1H · JTBD) → R2(SCAMPER 대체 · 결합 · 응용) → R3(수렴 · 균형) → R4(역발상 · 제거 · 극단 사용자 · 부정 공간)를 **항상** 순서대로 돈다. 프롬프트 4개는 서로 다르고, 역할 부여 없이 사고 절차를 적고, 도메인 예시 없이 형태 예시만 둔다. 각 프롬프트에는 버전 번호가 붙는다(D-020, B-003).
7. 분류를 물리 · 심리 · 행동 3축 × 하위 카테고리로 바꾸고, DCX-2(수동 추가 · 드래그) · DCX-3(접기) UI를 이 구조에 맞춘다(D-021).
8. HITL: 라운드 전 방향 지시, 라운드 후 승인/거절 + 사유 태그(관련성 낮음 · 흔함 · 문장형 · 오분류) + 자유 텍스트를 이벤트 로그로 남긴다. 라운드마다 `keyword_feedback.md`를 생성해 다음 라운드 프롬프트에 첨부한다(D-022).
9. R3 입력은 축 분포 · 거절 신호 · 사람 트렌드 누락 쿼리(검색광고 API). 빈 입력은 "없음 + 이유"로 적고, 어떤 입력으로 돌렸는지 기록한다(D-026, D-027).
10. 커버리지 지표 ① 검색량 가중 · ② 구간별 · ⑥ 축 분포 차이 · ⑦ LLM 단독 비율(D-025). 판정은 플래그만 한다. 검색량이 적어도 버리지 않는다(D-027).
11. 키워드 점수는 **키워드 단독** 월간 검색수(검색광고 API)로 바꾸고, 라운드마다 돌던 카페 검색 호출을 없앤다(D-014, D-026).
12. 확정 키워드는 `kw · kw_axis · kw_sub`와 함께 2단계로 넘긴다.

### 2단계 · 크롤링
13. 채널 어댑터: 네이버 카페 · 네이버 블로그 · 유튜브 댓글(yt-dlp 기본, Data API 선택) · 뽐뿌 · 클리앙(D-024, D-035). 0단계에서 고른 채널만 돈다. 어댑터를 끼워 넣는 구조로 만든다.
14. 오프라인 가짜 채널(LG 에어컨 CSV 기반)을 둔다. 테스트와 네트워크 없는 시연용이다(D-040).
15. 검색어는 키워드만 쓴다. 제품명 포함 필터는 기본 꺼짐이다(D-014).
16. **P1 목록 수집기**(별도 프로세스) → URL 큐(로컬 SQLite) · P1 스냅샷 → **검토 게이트**(키워드 × 채널 0건 · 저수율 · 고유 기여 표시, 사람이 제외) → **P3 상세 수집기**(별도 프로세스, 본문 · 댓글 · 대댓글) → P4 정규화 · 저장 → P5 리포트(D-026, D-032, D-033).
17. 두 수집기 모두 진행을 기록하고, 강제 종료 후 재시작하면 끊긴 지점부터 이어서 한다. 같은 스냅샷이면 같은 URL 목록이다.
18. P2 규칙 필터: 날짜 · 광고어(블로그 체험단 어휘 보강) · 제외/포함 **소스** · 정규화 URL + 채널 키 기준 중복 제거.
19. 새 문서 스키마: `doc_id · source · src_meta · kw · kw_axis · kw_sub · title · body · comments[] · date · url · fetch_level · access · crawled_at`. 심층 수집에 실패하면 스니펫으로 폴백(`fetch_level=snippet`)하고, 작성자 식별자는 수집 시점에 해시로 바꾼다(D-034).
20. 동시성 · 요청 간격 · 채널별 상한을 설정값으로 둔다. 100만 건 이상 규모를 전제로 설계한다(D-031).
21. 전처리 이후 코드가 새 스키마를 읽도록 최소한으로 고친다(D-034).

### 공통
22. LLM 호출 공통 층: `claude_api` / `codex_exec` 백엔드 선택. `codex_exec`는 cvc-agent 패턴(작업 1건 = exec 1개 · 미리 렌더링한 프롬프트를 통째로 주입 · run-id · pid 잠금 · 체크포인트 · 불량 격리 · 정체 감시)을 따른다(D-051).
23. 외부 API는 어댑터와 환경변수 자리만 만들고, 미연결이면 "미연결"로 표시한 채 계속 진행한다(D-023).
24. pytest 기반을 마련한다. 테스트는 네트워크 · API 키 · codex 설치 없이 돈다.

## 4. 대안

**A. 한 번의 하네스 실행 + 마일스톤 분할 (추천)**
- 마일스톤: M0 테스트 기반 · LLM 공통 층 → M1 0단계 · 컨텍스트 → M2 1단계 → M3 2단계 수집 기반(큐 · P1 · P3 · 스키마 · 가짜 채널) → M4 실제 채널 어댑터 → M5 뒤 단계 호환 · 0→2 통합 시연.
- 장점: 세 단계가 서로의 계약(키워드 축 메타 → 크롤링, 컨텍스트 → 모든 프롬프트)에 물려 있어 한 번에 맞추는 게 가장 덜 흔들린다. LG 에어컨 통합 시연이 하나의 수용 기준이 된다.
- 단점: 계획서가 크다. 마일스톤별로 Task를 나눠 리뷰한다.

**B. 단계별로 하네스 실행 3번 (0 → 1 → 2)**
- 장점: 승인 단위가 작다.
- 단점: 하네스는 체크아웃 하나에 실행 하나라 순차 대기가 길어진다. 1단계가 2단계 계약을 모른 채 먼저 굳는다.

**C. 크롤링 기반 먼저**
- 장점: 가장 오래 걸리는 수집 기반을 먼저 검증한다.
- 단점: 키워드 축 메타 · 채널 선택이 없는 상태에서 만들어 나중에 다시 손봐야 한다.

| AC-19 | 새 스키마 크롤링 결과로 전처리 단계가 에러 없이 돈다 | pytest |

| AC-21 | `pytest` · `npm run lint` · `npm run build`가 통과한다 | 하네스 `evidence` |

실제 사이트 소규모 수집(키워드 1~2개)은 수용 기준이 아니라 UAT 때 사용자와 함께 확인하는 항목이다. 사이트 응답은 매번 달라서 자동 기준으로 삼을 수 없다.

## 6. 제외 범위
- 3단계 이후 개편(임베딩 한 벌 · known_insights 검색 제외 · Jev/ChatGPT 교차 라벨링 · 캐스케이드 등). 뒤 단계는 새 스키마를 읽는 최소 수정만 한다.
- `KnownInsightsDrawer`(전 단계 공통 서랍) · RAG "아는 얘기로 넘기기".
- 0-A "방향성 경고"의 실제 표시(8단계). 경고 데이터 형태(`alignment_warnings[]`)만 정의한다(D-012).
- 채널 간 규모 균형(B-001) · 커버리지 지표 ③ ④ ⑤(B-002) · 프롬프트 A/B(B-003) · 1.0 사람 키워드 비교(B-005) · 피드백 세션 간 누적(B-006) · OpenAI API 배치 백엔드(B-007).
- 인스타그램 · Threads · 82cook.
- EC2 · S3 배포 경로 개선. 기존 코드는 지우지 않되 새 기능은 로컬 저장소 기준이다.
- 맥미니 절전 방지(사용자가 처리).
- 실제 외부 API 키 연결(개발자가 나중에 한다).

## 7. 위험
| 위험 | 영향 | 대응 |
|---|---|---|
| 범위가 크다(3단계 · UI · 크롤러 · LLM 층) | 계획 · 리뷰가 길어진다 | 마일스톤별 Task · 파일 소유권 분리. M3까지 끝나면 중간 보고 |

| 사이트 구조 변경 · 차단 · yt-dlp 동작 변화 | 실제 수집 실패 | 어댑터별 녹화 응답 테스트 + `fetch_level` 폴백 + 에러를 P5 리포트에 남긴다 |
| crawl4ai(Playwright/Chromium)를 맥미니에서 대량으로 돌리는 부하 | 처리량 저하 · 메모리 | 렌더링이 필요한 채널만 쓰고(커뮤니티는 httpx 우선), 브라우저 풀 크기를 설정값으로 둔다 |
| `codex exec`는 temperature · JSON 형식을 고정할 수 없다 | 출력 흔들림 | 스키마 검증 → 불량 격리 → 재시도(cvc 패턴). 사용량 한도는 B-007 |
| 외부 API가 전부 미연결인 상태로 개발한다 | 실제 연동 시 형식 불일치 | 공식 응답 형식 샘플로 계약 테스트를 만들고, 키가 들어오면 스모크 한 번으로 확인한다 |
| SQLite 큐에 100만 건 이상 쌓인다 | 조회 성능 | 상태 인덱스 · 배치 커밋. 규모 테스트는 합성 데이터로 한다 |
| 0단계 필드가 R1~R4 프롬프트로 어떻게 번역되는지(톤 분기 등) | 품질 차이 | 설계 문서에 필드 → 프롬프트 매핑 표를 둔다 |
