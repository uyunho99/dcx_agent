# DCX 2.0 · 0~2단계 개편 결정 기록

기획안(HTML)을 코드로 옮기면서 **구체화·수정·결정된 사항과 그 이유**를 모두 여기에 남긴다.
기획안 원본과 다른 결정을 했으면 반드시 "기획안과의 차이"에 적는다.

- 대상 기획안
  - `DCX2_0_0단계_입력_v2-2.html` (v2 → v2-2: `이미 아는 것(known_insights)` 필드 추가, 0-A 9필드 · 총 15필드)
  - `DCX2_0_1단계_키워드_v2.html`
  - `DCX2_0_2단계_크롤링.html`
  - 참고만: `DCX2_0_3-5단계_전처리_라벨링_학습.html` (0~2단계 산출물이 3~5단계 입력 계약을 만족해야 하므로 참조)
- 상태 표기: `확정` 사용자 결정 · `제안` Claude 제안, 사용자 확인 대기 · `보류` 백로그

---

## 범위

### D-001 이번 작업은 0~2단계만 수정한다 · 확정 (2026-09-28)
- 결정: 입력·키워드·크롤링만 바꾼다. 3단계 이후는 사용자가 기획 문서를 주면 이어서 수정한다.
- 이유: 현재 전달된 확정 기획이 0~2단계이고, 단계 구성 자체를 기획안 기준으로 바꾸는 것이 맞다는 판단.
- 영향: 0~2단계가 만드는 새 필드(0-A/0-B 값, `kw_axis`, `source`, `body`, `comments` 등)는 **저장까지 한다**. 뒤 단계 소비는 해당 단계 개편 때 연결한다.

### D-002 운영 환경은 맥미니 로컬 · 호스팅 없음 · 내부 실험용 · 확정 (2026-09-28)
- 결정: EC2/S3 호스팅을 전제로 설계하지 않는다. 맥미니 한 대에서 실행하고 저장도 로컬 디스크.
- 이유: 내부 실험용 도구. 저장 비용 문제는 맥미니 디스크로 해결.
- 영향: 저장소는 DCX-16에서 만든 `storage=local` 경로를 기본으로 쓴다. 작업 큐도 외부 서비스(SQS 등) 없이 로컬에서 끝낸다.

## 0단계 · 입력

### D-010 프로젝트 성격 · 분석 목적 · 타겟 스코프는 "선택 + 보충 서술" · 확정 (기획안대로)
- 결정: 기획안 ★ 권고안 그대로. 선택지(예: 브랜딩/신규기획/리뉴얼/UX개선)를 고르고, 옆에 자유 서술 칸을 둔다.
- 이유: 선택값이 있어야 1단계 발산 톤 분기(리뉴얼 → 기존 불만, 신규기획 → 미충족 니즈)를 코드 분기로 만들 수 있다. 서술 칸은 선택지로 담기지 않는 뉘앙스를 받는다.

### D-011 입력 부담은 고려하지 않는다 · 확정
- 이유: 상세히 입력할수록 분석에 도움이 된다. 필드 축소·간소화 UX는 하지 않는다.

### D-012 0-A는 "차단"이 아니라 "방향성 경고" · 확정 · 기획안과의 차이
- 기획안: "0-A는 위반을 차단한다 · 생성 결과가 선언을 벗어나면 오류"
- 결정: 결과를 막거나 버리지 않는다. 0-A(사내 제약·목적 등)에 어긋나는 결과에는 **"방향성과 맞지 않을 수 있음" 표시와 사유**를 붙여 보여준다.
- 이유: 제약을 하드 조건으로 넣으면 의외의 발견까지 잘려 나간다. 판단은 사람이 한다.
- 영향: 0~2단계에서는 0-A를 프롬프트 헤더에 싣는 것까지. 실제 경고 표시는 결과를 만드는 단계(주로 8단계)에서 구현하며, 공통 형태(`alignment_warnings[]`)만 지금 정의한다.

### D-013 `bk`(제품명)와 한줄 정의는 각각 적는 독립 필드 · 확정
- 결정: 둘 사이에 관계·파생 규칙을 두지 않는다. 사용자가 각각 입력한다.

### D-014 크롤링 검색어는 1단계 최종 키워드만 쓴다 · 확정 · 기존 코드 변경
- 기존: `"{bk} {kw}"` (예: "에어팟 러닝")
- 결정: `"{kw}"` (예: "러닝")
- 이유: 제품명을 붙이면 제품을 직접 언급한 글만 모여 "제품 밖 경험"을 발견할 수 없다. 관련성은 4단계(anchor 판정)가 문서 단위로 판단한다(3~5단계 기획의 "타겟 무관 단어를 규칙으로 지우지 않는다"와 같은 원칙).
- 연쇄 변경:
  - 2단계 P2 필터 ⑤ "제품명 포함"은 **기본 꺼짐**으로 바꾼다. 켜 두면 "러닝"으로 모은 글 대부분이 제품명이 없어 탈락하므로 D-014와 충돌한다. (기획안과의 차이, 옵션으로만 남김)
  - 1단계 키워드 검색량 점수도 `"{bk} {kw}"`가 아니라 **키워드 단독** 검색량으로 잰다(1단계 기획 V1 "키워드 자체 월간 검색수 · {bk} 대비 비율"과 일치).

### D-015 제품군 대›중›소 분류 · 제안
- 사용자 의견: 분류표를 우리가 들고 있기보다 자연스럽게 분류되길 원함.
- 제안: 제품명(`bk`)과 한줄 정의를 넣으면 **자동으로 대›중›소를 제안**하고 사용자가 확인·수정한다.
  - 기준점: 네이버 쇼핑 검색 API가 상품마다 돌려주는 `category1~4`(네이버 쇼핑 표준 분류). `bk`로 검색한 상위 상품의 최빈 카테고리 경로를 후보로 쓴다.
  - API 키가 없거나 결과가 없으면 LLM이 추정하고 "추정" 표시.
  - 이유: 우리가 분류표를 관리하지 않아도 되고, 사람들이 실제로 쓰는 쇼핑 분류라 기준이 흔들리지 않는다. 프로젝트 간 같은 제품군이 같은 이름으로 묶인다.

### D-017 0-A 맥락 전달 방식: `project_context.md` 파일 + 호출 시 원문 첨부 · 확정 (2026-09-28 동의)
- 사용자 의견: 1·6·7·8단계 프롬프트 맨 위에 매번 붙이기보다 AGENTS.md 같은 파일을 두고 "한 번 읽게" 하는 게 낫지 않나. 강제 규칙이 아니라 참고용이므로.
- 검토한 사실
  1. DCX의 LLM 호출은 API 호출(`services/claude.py`)이다. 모델이 파일을 열어 읽지 못하므로, 어떤 방식이든 **내용이 결국 요청 본문에 들어가야** 모델이 본다.
  2. cvc-agent에서 이미 겪은 일: "파일을 읽어라"로 지시하면 워커가 일부만 조각 읽기하고 나머지를 안 본 채 답했다(cx20 row-0). 그래서 cvc는 본문을 지시문에 통째로 싣는 방식으로 바꿨다(`codex/README.md`).
- 제안
  - 0단계 15필드로 세션마다 `project_context.md`를 **생성**한다(사람이 읽고 확인할 수 있는 AGENTS.md 역할).
  - LLM을 호출하는 공통 함수가 이 파일을 **"참고 맥락" 블록으로 원문 그대로** 첨부한다. 문구는 "규칙"이 아니라 "참고하되 벗어나는 발견은 배제하지 말 것"(D-012와 일치).
  - 단계별로 필드를 고르지 않고 파일 전체를 싣는다. 1~2KB 수준이라 비용이 작고, 프롬프트 캐시를 쓰면 반복 비용이 더 준다.
- 이유: 사용자가 원하는 "파일 하나로 관리 · 참고용" 성격은 지키면서, 모델이 실제로 내용을 보는 것을 보장한다.

### D-016 `known_insights`(이미 아는 것) 입력 칸 · 확정 (기획안 v2-2)
- 0단계는 선택 입력 칸만 만든다. `session.json.knownInsights[]`에 `{id, type:"statement", text, from:"stage0"}`로 저장.
- 전 단계 공통 서랍(`KnownInsightsDrawer`)·RAG 넘기기는 3단계 이후 개편 범위.

## 1단계 · 키워드

### D-020 R1 → R2 → R3 → R4는 항상 순서대로 모두 돈다 · 확정 · 기존 코드 변경
- 기존: 총합 160개 미만일 때만 R4.
- 이유: 라운드마다 프롬프트 역할(발산/인접 확장/수렴/재발산)이 달라서 건너뛰면 설계가 무너진다.

### D-021 3축 분류로 교체 · 확정
- 7개 flat 카테고리 → 물리·심리·행동 3축 × 하위 카테고리. DCX-2(수동 추가·드래그)·DCX-3(카테고리 접기) UI를 이 구조에 맞춰 수정한다.

### D-022 HITL 구조를 기획에 추가 · 확정 · `keyword_feedback.md`는 사용자 제안 채택
- 라운드 전 방향 지시 · 라운드 후 승인/거절 + 사유 태그 + 자유 텍스트를 **이벤트 로그(JSON)로 누적**한다.
- 사용자 제안: AGENTS.md처럼 `keyword_feedback.md`를 만들어 참고하게 하자.
- 결정: 이벤트 로그를 원본으로 두고, 라운드가 끝날 때마다 `keyword_feedback.md`를 요약 **생성**한다(거절 사유별 건수와 예시, 방향 지시 목록, 자유 텍스트). R2~R4 프롬프트에는 D-017과 같은 방식으로 이 파일을 원문 첨부한다.
- 이유: 사람이 읽을 수 있는 한 파일로 누적 판단을 확인할 수 있고, 모델에게도 같은 내용이 그대로 간다.

### D-026 R3 `{coverage_signals}` 구성 조정: 크롤링 신호 제외 · 확정 (2026-09-28 동의) · 기획안과의 차이
- 기획안: R3 입력 `{coverage_signals}` = "커버리지 누락 쿼리 + 2단계 0건 · 고유 기여 플래그"
- 사용자 문제 제기: 크롤링 전 3V 검토의 목적은 키워드가 유의미한지 보는 것인데, R3 때문에 미리 검색하고 R4 뒤에 또 검색하면 비용·시간이 두 번 든다.
- 검토한 사실
  - 커버리지 신호는 두 종류다. ⓐ 사람 트렌드 누락 쿼리(검색광고 API): 크롤링이 필요 없다. 키워드 5개당 1회 호출이라 수백 개도 수십 회로 끝난다. ⓑ 0건 · 고유 기여: 목록을 실제로 모아 봐야 안다.
  - 지금 코드는 라운드마다 모든 키워드를 카페 검색 API로 한 번씩 조회해 점수를 매긴다. 이미 키워드당 검색 1회를 쓰고 있다.
- 제안
  1. R3에는 ⓐ만 넣는다. 키워드 점수도 검색광고 월간 검색수로 바꿔 카페 검색 호출을 없앤다.
  2. ⓑ는 2단계로 옮긴다. R4 승인 후 **P1 목록 수집 → 검토 게이트 → P3 심층 수집** 순서로 돈다. P1이 끝나면 0건 · 저수율 · 고유 기여 낮음 키워드를 표시하고, 사람이 빼면 비싼 P3을 그 키워드에 쓰지 않는다.
  3. P1에서 모은 URL 목록은 P3이 그대로 이어서 쓴다(D-033). **어떤 키워드도 두 번 검색하지 않는다.**
  4. 덤: 같은 `bk`로 돌린 이전 세션이 있으면 그 세션의 P5 결과(0건 키워드)를 R3에 무료로 넣을 수 있다.
- 이유: 기획 취지(데이터가 본 신호로 발산 실패를 잡는다)는 유지하면서 검색을 한 번으로 줄인다. 판단 시점이 "R3 수렴"에서 "P3 전 게이트"로 옮겨질 뿐, 비싼 수집 전에 걸러진다는 효과는 같다.

### D-027 검색량이 적어도 키워드는 버리지 않는다 · 확정
- 월간 검색수가 적은 키워드는 "LLM 단독 · 검색량 적음" 배지만 달고 사람이 채택 여부를 정한다. 자동 탈락 없음(기획안 "판정은 게이트가 아니라 플래그"와 일치).
- R3 입력이 비었을 때(C1): 빈 칸을 조용히 빼지 않고 "없음 + 이유"를 적는다. 거절이 0건이면 사용자가 직접 추가하거나 옮긴 키워드를 "원하는 방향" 신호로 넣는다. 커버리지 API가 미연결이면 "커버리지 정보 없음 · 축 분포 균형에 집중"으로 적는다. 어떤 입력으로 R3를 돌렸는지 세션에 기록한다.

### D-023 외부 API는 코드만 만들고 연결은 나중에 · 확정
- 네이버 검색광고 · 데이터랩 · NAVER API HUB · YouTube Data API: 어댑터와 환경변수 자리만 만든다. 키가 없으면 해당 기능은 "미연결"로 표시하고 파이프라인은 계속 진행한다.

### D-024 유튜브는 API 할당량에 묶이지 않는 수집 경로를 만든다 · 확정 · 기획안과의 차이
- 기획안: YouTube Data API(search.list 일 약 100회 → 상위 키워드만)
- 결정: 쿼터 없는 수집기를 기본 경로로 둔다(후보: `yt-dlp` 검색 + 댓글 추출). Data API는 선택 어댑터로 남긴다.
- 이유: 하루 100회 검색으로는 세션 키워드(수백 개)를 다룰 수 없다.

### D-025 커버리지 지표는 일부만 먼저 구현 · 확정 (Claude 추천 채택)
- 먼저: ① 검색량 가중 커버리지 · ② 구간별 커버리지 · ⑥ 축 분포 차이 · ⑦ LLM 단독 비율
- 백로그: ③ 순위 일치도(RBO) · ④ 결과 문서 겹침 · ⑤ 신선도

## 2단계 · 크롤링

### D-033 크롤링은 "목록 수집 → 별도 프로세스 상세 수집" 2단 · 확정 (사용자 작업 방식)
- 사용자가 실제로 쓰는 방식: 키워드별로 글 URL 목록을 먼저 전부 모은 뒤, 별도 프로세스가 하나씩 들어가 본문을 긁는다. 기획안의 P1(탐색) · P3(심층)과 같은 구조다.
- 결정
  - P1 목록 수집기와 P3 상세 수집기를 **서로 다른 프로세스**로 둔다.
  - URL 큐를 로컬 SQLite에 둔다(URL · 키워드 · 채널 · 상태 · 시도 횟수 · 마지막 오류).
  - 두 프로세스 모두 중간 진행을 기록하고, 재시작하면 끊긴 지점부터 이어서 한다.
  - P1 결과(URL 목록)는 스냅샷으로 저장된다. 같은 스냅샷으로 P3를 다시 돌리면 같은 URL 목록이 된다(D-032).
- 맥미니 절전 방지는 사용자가 직접 처리한다(코드 범위 아님).

### D-034 크롤링 결과는 새 스키마로 전환하고 뒤 단계를 그 형식에 맞춘다 · 확정

### D-076 LLM 기본 백엔드는 GPT API · 확정 · G3 대체
- 사용자: "기본 api는 gpt api야. 그리고 설정으로 codex exec를 사용해도 되고."
- 영향: LLM 공통 층의 백엔드 = `openai_api`(기본) · `codex_exec` · `fake`. 기존 `claude_api`는 3단계 이후 코드가 쓰던 경로로 남기되 0~2단계 기본값이 아니다. 02-design 3절, 03-plan T02 · Global Constraints를 고친다.

### D-077 크롤링은 여러 채널 · 여러 키워드를 동시에 · 확정
- 사용자: "가능하면 여러 개의 채널, 여러 개의 키워드를 동시에 해서 시간을 단축."
- 영향: P1 · P3 모두 채널끼리 병렬, 채널 안에서는 키워드 · URL을 채널별 동시성 한도까지 병렬로 처리한다(채널별 요청 간격은 유지).
- 사용자: "사이트 구조 변경 · 차단이 제일 어렵고 계속 코드를 수정해야 할 것 같다." → 어댑터는 사이트마다 분리하고, 사이트 구조가 바뀌었는지 빨리 알 수 있는 채널 점검 스크립트(키워드 1개로 목록 · 본문 파싱 성공 여부 보고)를 둔다.

### D-070 보완 — 모든 단계 결과는 임시 저장 · 저장으로 남긴다 (D8)
- 사용자: "모든 결과는 임시저장이나 저장을 무조건 만들어야 한다."
- 영향: 서버가 저장을 거부해 결과가 사라지는 경로는 없어야 한다. 0~2단계는 이번에 임시 저장 · 저장 + 버전 기록으로 만든다. 3단계 이후 화면은 이번 범위 밖이므로(D-001) 기존 통째 저장을 받아 주되 서버가 쓰는 칸은 보호한다(D8 답 A). 그 단계들을 개편할 때 같은 저장 · 버전 구조로 옮긴다.

### D-078 버전 = 세션 내용 통째 복사, 크롤링 수집본만 모듈로 분리해 조합 · 확정 (사용자, 2026-09-29)
- Claude 제안(단계 결과 스냅샷 조합)이 아니라 사용자 안으로 확정: "통째로 복사하는데, 크롤링 파트만 모듈화해서 조합하는 방식."
- 구조
  - 세션 안에 버전 `v1, v2, …`가 있고, 각 버전은 세션 상태(입력 · 키워드 · 이벤트 · 3단계 이후 결과 전부)의 **완전한 복사본**이다.
  - 크롤링 수집본은 세션 아래 별도 모듈 `collections/c1, c2, …`로 두고 **변경하지 않는다**. 버전은 `collectionId`로 가리키기만 한다. 여러 버전이 같은 수집본을 쓸 수 있다.
  - "N단계부터 다시" = 현재 버전을 통째로 복사해 새 버전을 만들고, 복사본에서 N단계 이후 결과를 "이전 기준" 표시와 함께 보관한 채 다시 진행한다.
  - 과거 버전은 읽기 전용으로 열람하고, 두 버전을 단계별로 비교할 수 있다.
- 키워드 변경 후 수집: 기본은 기존 수집본 재사용. 선택하면 "추가된 키워드만 수집" → 새 수집본 `c2 = c1 + 추가분`(c1은 그대로).
- 엔지니어링 리뷰 Codex 지적 2번(목록 재수집 시 스냅샷 경계 없음)은 이 구조로 해소된다: 목록을 다시 모으면 새 수집본이 생기고, 전처리는 버전이 가리키는 수집본만 읽는다.

### D-079 URL 한 번만 수집 · 공유 URL 제외 규칙 · 키워드별 개수는 중복 포함 · 확정 (D9)
- 사용자: "이중 크롤링을 방지하려고 URL부터 수집하고 URL마다 원문을 수집하는 것이니 중복이 애초에 없어진다. 키워드당 원문 개수 카운팅은 중복으로 해도 된다."
- 규칙: URL은 한 번만 수집한다. 게이트에서 키워드를 빼면, 그 URL을 찾은 키워드가 모두 빠졌을 때만 URL이 빠진다. 문서에 찾은 키워드 목록(`kw_hits`)을 남기고, 키워드별 개수는 중복을 포함해 센다.

## 구현 단계 결정 (Main Claude 판정, 2026-09-29) — 사용자 확인 필요 시 되돌릴 수 있음

구현 중 리뷰에서 나온 모호점을 설계(02-design)를 기준으로 판정했다. 전체 목록과 근거는 SDD 원장(`.superpowers/sdd/03-plan/progress.md`, git 제외)의 `Ruling R-xx`에 있다. 제품 동작에 영향이 있는 것만 옮긴다.

### D-080 과거 버전은 "활성화"하지 않고 열람만 (R-23)
- 과거 버전은 `?version=`으로 읽기만 한다. 활성 버전 전환은 쓰기 가능한 버전으로만 된다. 되살리기 = 과거 버전에서 새 버전 만들기.
- 이유: 읽기 전용 버전이 활성이면 3단계 이후 화면의 통째 저장이 거부돼 결과가 사라진다(D-070 위반).

### D-081 1단계 라운드 "다시 생성" 허용 (R-45)
- 생성은 끝났지만 확정하지 않은 라운드는 `?regenerate=true`로 다시 생성할 수 있다(세대 +1). 확정한 R1~R3는 다시 생성할 수 없다.
- 이유: 8.1 상태 문구와 목업 S2가 "R{n} 다시 생성"을 전제로 한다. 5.2 흐름은 이를 막지 않는다.

### D-082 피드백 md의 거절은 키워드당 최신 1건 (R-28 · R-44)
- 나중에 되돌리기 · 다시 추가 · 승인된 거절은 빼고, 같은 키워드의 거절은 최신 1건만 센다. 이벤트 로그 자체는 모두 남긴다.
- 이유: 화면 이벤트와 확정 이벤트가 겹쳐 "2건"으로 부풀어 다음 라운드 LLM 입력을 왜곡했다.

### D-083 검색량 "< 10"은 PC · 모바일 각각 4로 추정 (R-30)
- 두 쪽 모두 "< 10"이어도 합계 8로 저검색량(< 10) 배지를 받는다.

### D-084 제품명 포함 필터는 본문(P4)에서만 (R-25 관련 T11 판정)
- 목록 단계에서 제목 · 스니펫으로 거르지 않는다(02-design 6.5).

### D-085 기존 광고어 목록 = 옛 크롤링 화면 기본값 + 기획 추가어
- 옛 서비스 코드에는 광고어 목록이 없고 화면 기본값(`협찬, 광고, 제공받, 원고료, 체험단, 서포터즈, 중고, 판매, 거래`)만 있었다. 이를 이어 받고 `체험단 협찬 원고료 소정의 제공받아 서포터즈`를 더했다. P4 본문에도 적용되므로 "중고 · 판매 · 거래"가 들어간 실제 후기도 빠질 수 있다 → UAT에서 확인.

### D-086 전처리 본문 최소 길이 10자, 스니펫은 기존 기준 유지 (T18)
- 원문 문서의 저품질 컷 = 본문 10자 미만. 스니펫 문서는 옛 기준(제목 5자 미만 **그리고** 설명 10자 미만이면 제외)을 그대로 쓴다.

### D-087 크롤링 한도는 워커가 지킨다 (R-50)
- 키워드당 최대 URL(채널별), 유튜브 영상 수 · 댓글 수, 목표 건수(도달 시 P3 정상 종료). 설정은 목록 수집 시작 시점 값으로 고정된다(추후 개선 후보).

### D-088 첫 임시 저장(세션 생성 전)은 브라우저에 보관 (R-37)
- 0단계에서 아직 한 번도 저장하지 않은 새 폼의 "임시 저장"은 이 브라우저 저장소에 둔다. 첫 저장부터 서버 초안으로 옮긴다.
