## CLI and exit codes

```text
python -m app.crawl.worker list --sid S [--collection DIR]
python -m app.crawl.worker detail --sid S --snapshot ID [--collection DIR]
python -m app.crawl.healthcheck [--source fixture] [--keyword 에어컨]
```

List prints its snapshot ID. Worker exit 0 means normal completion, graceful SIGTERM, or completion of the remaining channels after a channel pause. Exit 1 means an execution/configuration/fencing error; the error appears on stderr. Argparse exits 2 on invalid arguments, including detail without a snapshot. SIGKILL has the operating system's signal termination status.

Healthcheck exits 0 when attempted stages succeeded, 1 when a stage failed, and 2 on invalid CLI arguments. A successful fixture line is `fixture: list_ok 80/80 · detail_ok 3/3 · blocked false`. Stage exceptions print `FAIL` for that stage; `AdapterBlocked` sets `blocked true`. With fewer than three list items the detail numerator is the number actually fetched, still over `/3`.

Without an override the worker calls `load_session(sid)` and resolves `Path(settings.local_data_dir)/"crawl"/sid/"collections"/collectionId`. A missing collectionId is a clear error, never an implicit collection creation. `queue.sqlite` and `docs/` are inside that directory.

List keywords/channels come from `manifest.json` when provided, otherwise session keywords and crawlConfig channels, finally available adapters for unspecified channels. Manifest `config` (or session `crawlConfig`) accepts `filters` matching FilterConfig and `channel_limits[source] = {concurrency, min_interval_s}`. Direct Python calls also accept explicit keywords, sources, filters, limiters, collection; detail accepts a backoff base for deterministic tests. Defaults are max_attempts 3, backoff base 1 second with queue-managed exponential delay, 4 fixture workers, 10-second heartbeats, 60-second reclaim checks, and 5,000-document shards. The queue's STALE_AFTER_S remains 60 and is not overridden.

## T14 channel-state contract

`worker_state.json` beside `queue.sqlite` is atomically replaced using the existing fsync-and-rename storage helper:

```json
{
  "sid": "S",
  "kind": "detail",
  "run_id": "...",
  "snapshot_id": "...",
  "channels": {
    "fixture": {"status": "done", "attempts": 80, "parse_errors": 0, "blocked": 0}
  }
}
```

T14 should read `channels[source].status`, not infer success from the run being finished. Statuses are `running`, `done`, `stopped`, `interrupted`, `failed` (terminal list-task failures), `paused_blocked`, and `paused_parse_error`. Block count means consecutive AdapterBlocked responses; other outcomes reset it. At 20 the channel pauses. ValueError (including AdapterParseError) and TypeError count as parser failures; a rate strictly greater than 30% after at least 10 attempts pauses the channel. Adapter return-shape violations are AdapterParseError. Network/OS exceptions retry without being misclassified as parse failures. Already in-flight requests may finish after the threshold, while no further adapter requests are dispatched for the paused channel. Other channels continue.

The file describes the latest worker invocation; an explicit new invocation starts fresh channel counters. It is not an accumulated report or a simultaneous P1/P3 state store. Runs, PID, heartbeat, and completion status remain in SQLite through public queue methods. P1 and P3 for the same collection should be sequenced by T14.

## Scheduling and ownership

Each channel has its own thread pool sized by ChannelLimiter. Its semaphore and serialized request-start clock enforce concurrency and spacing; the clock and sleep function are injectable. Only adapter work happens in pool threads. The coordinator performs every SQLite operation, normalization, file write, and commit.

P1 uses `next_list_tasks(source, n)` and reports failures with `mark_list_failed`. P3 uses global `lease_urls` because the queue has no source filter, buffers by channel, and selects fair waves of at most 200 URLs. It scans past dense ordered source groups to let channels overlap even across the original queue batch boundary. Heartbeats continue while waiting for slow futures and while scanning claims. Dead-run recovery is performed by registration, with periodic public reclaim during execution. Leases are 86,400 seconds to avoid premature expiry of slow healthy adapter requests; dead/stale ownership is still reclaimed immediately on restart or at the queue's 60-second stale threshold.

LeaseLost aborts acquisition and completion. Pending batches are never committed in cleanup; the run is finished as interrupted and CLI exits 1. SIGTERM stops new dispatch, collects already running results, durably commits their batch, and finishes as stopped. Claims that were not fetched remain recoverable.

## Batch/fsync/commit sequence

1. Fetch (or skip directly to snippet fallback for recovered exhausted rows).
2. Run `check_doc`; fully filtered URL results use `mark_filtered`.
3. Build validated Doc records using deterministic doc_id, hashed author, cleaned text, representative kw, and all kw_hits. Restricted records are preserved as snippet-level documents.
4. Append to `docs/shard-XXXX.jsonl` through `DocWriter(dir, shard_size=5000)`.
5. Flush and fsync files (and directory entries) before one deduplicated `mark_done_many` completion transaction; clear a committed batch immediately. Waves and completion batches never exceed 200 URLs; long multi-thread URL results also flush every 200 document writes.
6. On a fetch exception use `mark_failed_attempt(max_attempts=3)`. Pending rows wait for exponential retry eligibility. Exhausted rows retain ownership, write a snippet, then complete after fsync with last_error.

No committed batch is retried. An interruption can re-fetch only the current bounded fetch wave; committed URLs are not fetched again. Append-only files may contain repeated doc IDs after a crash. `read_docs` skips invalid UTF-8/JSON/non-document records with warnings and yields the first copy of each doc_id. Opening a shard whose last byte is not newline appends a newline before new records. Rotation fsyncs the previous shard before closing it.

## Subprocess test hook

`DCX_TEST_ADAPTER_MODULE` is inert unless set. When present the worker imports that module before constructing adapters; the module can register factories in REGISTRY. The SIGKILL regression supplies a temporary module on PYTHONPATH and uses an append-only fetch log. It kills the actual `python -m app.crawl.worker` process after approximately 30 fetches, restarts it on the same snapshot, verifies each URL was fetched once except at most one wave, and verifies 80 unique documents after reading/deduplication. Tests generate their own CSVs and require no external corpus or network.

## Concerns

- The existing Pydantic class-based Config deprecation in app/config.py is the only test warning; it is outside this task's ownership.
- The source-less queue API requires buffering claims while scanning past a dense source. This can use memory proportional to that ordered group. These buffered URLs are not fetched until a bounded wave, but queue leasing increments their attempt count. Paused/unstarted claims remain leased until public reclaim at the next run (or expiry). A future source-selective lease/release API could reduce these costs; this task does not patch the reviewed queue API.
- Adapters must enforce their own network timeouts. Python cannot forcibly cancel an already running thread. SIGTERM drains those requests; fencing prevents their results from being completed after ownership loss.
- worker_state.json is latest-run state, so T14 should not start P1 and P3 simultaneously for one collection.
