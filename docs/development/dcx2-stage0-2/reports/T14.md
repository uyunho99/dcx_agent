## API

Mutation routes accept `?version=vN`; past/readonly and legacy sessions return 409. Errors have `{status:"error",error:{kind,message}}`. Malformed bodies and invalid config return 422; missing sessions/snapshots return 404; lifecycle conflicts return 409; storage/process OS errors return 500. `/crawl` POST and `/status/{sid}` GET return 404.

| Method | Path | Body/query | Response | Additional errors |
|---|---|---|---|---|
| PUT | `/crawl/{sid}/config` | `{channels,dateFrom?,dateTo?,adWords?,excludeSources?,includeSources?,product_name_filter?,perChannel?,youtube?,target_total?}` | `{status:"ok",crawlConfig}` | 422 unavailable source, reversed dates, invalid limits |
| POST | `/crawl/{sid}/list` | no body; optional `mode=added-keywords` | `{collectionId,kind:"list",status:"running",pid}` | 409 live worker/missing parent; 422 no approved new keywords |
| PUT | `/crawl/{sid}/gate` | `{exclusions:[kw,...]}` | `{status:"ok",exclusions}` | 409 P1 unfinished or P3 already started; 422 unknown keyword |
| POST | `/crawl/{sid}/detail` | `{snapshot_id}` | `{collectionId,kind:"detail",status:"running",pid}` | 409 partial/stopped P1, changed snapshot, finished collection, use-resume conflict |
| GET | `/crawl/{sid}/status` | none | status object below | 404 session |
| POST | `/crawl/{sid}/resume` | none | `{collectionId,kind,status:"running",pid}` | 409 no unfinished phase |
| POST | `/crawl/{sid}/stop` | none | `{collectionId,status:"stopping"\|"idle"}` | same version/lifecycle validation |

Config accepts `sources` as an alias for `channels`, and `productNameFilter` as an alias for `product_name_filter`. Gate accepts `gateExclusions`; detail accepts `snapshotId`. Product filtering defaults false. Dates default to the last 365 days; explicit null disables a bound. Per-channel concurrency is 1–64, intervals are nonnegative, throughput estimates are positive. Only `available_sources()` can be selected. Config is captured in the collection manifest, translated to T13 `filters` and `channel_limits`, and never prepended to keyword queries. Product context bk is passed only to the body filter.

## Collections and versions

```text
data/crawl/{sid}/collections/c1/
  meta.json
  manifest.json
  .control.lock
  queue.sqlite
  list.log
  detail.log
  worker_state.json
  gate.json
  docs/shard-XXXX.jsonl
  report.json
```

`meta.json` contains `{id,parent,createdAt,keywords,status}`. Keywords are full approved keyword records carrying kw/axis/sub, in session confirmation order; duplicate text is removed while retaining the first record. The manifest adds `{channels,config,snapshotId}` for T13. Status initially is `list`; the selected detail snapshot and phase are stored in the manifest. Report finalization sets both metadata statuses to `done`.

Every P1 launch allocates the next cN. Added-keywords mode follows all parent metadata, removes every keyword already in that chain, and links the current collection as parent. Previous docs and queues are not copied or rewritten. Finished collections reject further detail, gate, and resume mutations. Starting another P1 creates another collection. Pending P5 finalization is completed before replacing the active pointer.

All session writes go through `store.update_session`. A locked merge callback, matching T09's established pattern, validates versions and computes patches inside the store lock. The collection pointer is persisted before Popen; launch reacquires the store lock and revalidates the version and pointer. A version/pointer change in that small interval rejects launch and leaves the prepared collection intact.

## Worker control

Popen uses `[sys.executable,"-m","app.crawl.worker",kind,"--sid",sid,"--collection",absolute_directory]`, plus `--snapshot` for detail, backend cwd, `start_new_session=True`, and stdout/stderr redirected to the collection phase log.

The collection flock covers checking the queue runs table, checking PID liveness, and spawning. A SQLite `BEGIN IMMEDIATE` spans Popen and insertion of a `starting` reservation with the child PID. The worker registers its own `running` row once the transaction commits; it does not collide with the reservation. Queries ignore reservations superseded by that PID's real run. Both mocked concurrent calls and actual CLI list/detail subprocesses are tested. A live worker is returned without another spawn; a live different phase rejects the request.

Stop sends SIGTERM to the worker PID; only the worker marks its run stopped after committing the batch. Resume reclaims abandoned/expired leases and launches the saved kind with the manifest's detail snapshot. A stopped P1's partial snapshot remains visible, but cannot bypass the gate sequencing rule to launch P3.

## Status payload for T22

```text
{
  status: "running" | "interrupted" | "done" | "idle",
  kind: "list" | "detail" | null,
  collectionId: "cN",
  snapshot_id: string | null,
  updatedAt: ISO timestamp,
  progress: {
    done, target, full, snippet, restricted, per_minute,
    list_tasks: {source: {done,target}},
    channels: {source: {status,attempts,parse_errors,blocked}}
  },
  channels: {source: {status,attempts,parse_errors,blocked}},
  gate: [{kw,axis,sub,per_source:{source:{listed,filtered,unique}},
          listed,after_filter,unique_ratio,badges}] | null,
  estimate: {urls,minutes} | null,
  report: {matrix,channels,totals,counts,snapshot_id,
           started_at,finished_at,throughput_per_min} | null
}
```

Before a collection exists, status is idle, kind/progress/gate/report are null, channels is empty, and updatedAt comes from the session. A dead worker with an unfinished run is interrupted; stale heartbeat also shows interrupted. A completed run remains done even when its PID has exited. Worker channel state is read from `worker_state.json`, preserving paused/failed states rather than inferring channel success. Active phase completion advances the session step to crawl-gate/crawl-done; historical/readonly session state is not overwritten.

Progress counts completed URL rows, not documents: `done`, `full`, `snippet`, and `restricted` match queue status/fetch_level/access aggregates. Target is total URLs minus filtered/excluded. Multi-document URL totals separately appear in `report.totals.doc_count`. Throughput is completed URLs per elapsed run minute, frozen at final heartbeat after completion. No docs are read. `activity(sid)` is a read-only `{kind:"crawl_list"|"crawl_detail",status,progress,updatedAt}` or None, including None for collection references without a queue. This preserves T04 version/list behavior without nested session-lock acquisition.

## Gate and report persistence

Gate thresholds are exactly count < 10 and unique ratio < 0.2, with badges `zero`, `low`, `low_unique`. Shared URLs count once per discovering keyword through url_hits; unique contribution goes to the first keyword in confirmation order. Zero-hit keywords/sources remain in the table. Filtered means removed by filters; after_filter is listed minus filtered. Gate is cached at P1 completion in gate.json, or just before detail starts, so P3 mutations cannot change the reviewed table. Gate save records crawlConfig.gateExclusions and keywords[].crawlExcluded, without spawning. Detail applies saved exclusions with the queue's D9 shared-URL behavior.

`build_report(queue)` uses SQL aggregates exclusively. Matrix cells have exactly `listed,filtered,excluded,full,snippet,restricted,unique`. Channels include docs/share/status/errors_top; totals deduplicate shared URLs and sum doc_count. `counts[kw][source]` is included for T04 stage2 comparisons. Estimates exclude saved gate keywords and deduplicate surviving URLs, using per-channel per_minute (default 60) and the slowest concurrent channel.

`write_report(sid)` takes the collection lock, returns the existing report if present, and only builds when the latest actual run is detail/done. Status detects completion and calls the same locked helper using its already selected collection, preventing active-pointer races. Starting a new list also finalizes an unreported completed predecessor. The JSON write uses the store's fsync/atomic-replace helper; concurrent/repeated polls do not rewrite it. Reports are absent while P3 is running or stopped. Worker files were not modified.

## Concerns

- T13 currently does not enforce `target_total`, per-channel `max_per_keyword`, or YouTube limits. T14 validates and persists these for the worker/adapter contract; changing T13 was outside ownership. Concurrency, intervals, filters, and explicit snapshots are wired through.
- Report creation is completion-detected: a status read, explicit write_report, or next list start finalizes it. There is no independent watcher after the worker exits.
- T13 marks normally exited paused-channel invocations done; the report retains paused channel states and pending queue counts. Such a finalized collection is immutable; collecting again requires a new collection.
- The queue records fetch_level/access per URL, so mixed multi-document URL outcomes cannot be split into document-level full/snippet counts without a queue schema change.
- PID checks have the usual PID-reuse limitation. JSON metadata, session pointer, and process creation are not a single crash-atomic transaction. A prepared but unlaunched collection is preserved if launch revalidation or Popen fails.
- Existing app/config.py Pydantic class Config deprecation is outside scope.
- The old frontend still calls removed routes until its later migration; no frontend file was changed.
