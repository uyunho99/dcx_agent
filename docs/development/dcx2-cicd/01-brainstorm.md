# DCX 2.0 CI/CD — GitHub 테스트 + 맥미니 자동 배포

- 실행: `dcx2-cicd` · 기준 커밋 `2ba66eb`(main, PR #5 머지 후)
- 결정 기록: 같은 폴더 `decision-log.md` D-401~
- 참고 구조: 같은 맥미니의 `~/srv/internal-app`(`person-a-ai/internal-app`)이 이미 쓰는 방식

## 1. 문제

| 지금 | 생기는 일 |
|---|---|
| 저장소에 CI가 없다 | PR을 머지해도 아무도 테스트를 돌리지 않는다. 이번 PR #5도 머지 직전 손으로 돌린 결과만 근거였다. |
| main에 머지해도 어디에도 반영되지 않는다 | 데모 서버(3311 · 8311)는 개발 폴더의 다른 브랜치에서 돌고, 사람이 브랜치를 바꾸고 서버를 다시 띄워야 새 기능이 보인다. |
| 배포 폴더 `~/srv/dcx-agent`(화면 3400 · 백엔드 8400)는 2026-10-02에 손으로 한 번 띄웠다 | `nohup`으로 띄운 프로세스라 맥미니를 재부팅하면 꺼지고, 다음 머지 때도 손으로 다시 해야 한다. |
| `scripts/deploy.sh`는 1.0 시절 EC2용이다 | 지금 운영 방식(맥미니 로컬 전용)과 맞지 않는다. |

## 2. 무엇을 만드나

```
PR · main 푸시 ──► GitHub Actions CI (GitHub 서버)
                     pytest · lint · vitest · build
                         │ 결과(초록/빨강)
                         ▼
맥미니 launchd 1분 타이머 ──► main 머리 커밋 확인 ──► CI 초록?
   (LaunchDaemon, 로그인 불필요)        │ 아니면 대기
                                       ▼ 초록
                         세션 스냅샷 → 새 릴리스 빌드 → 교체 → 상태 확인
                                       │ 실패
                                       ▼
                         이전 릴리스(+그 스냅샷)로 롤백, 로그 기록
```

### 2-1. CI (GitHub Actions, GitHub 서버에서 실행)
- 대상: PR(모든 브랜치 → main)과 main 푸시.
- 하는 일: 승인된 검증 명령 4개 그대로 — 백엔드 `pytest backend/tests -q`, 프론트 `lint` · `test` · `build`.
- 네트워크 · 키 없이 돈다(지금 테스트가 이미 가짜 백엔드로 돈다). 저장소 비밀값을 쓰지 않는다.

### 2-2. CD (맥미니, 들어오는 연결 없음)
- `~/srv/dcx-agent` 구조: `repo/`(git), `releases/<sha>/`(커밋별 빌드), `current` → 지금 릴리스, `shared/`(`app.env` 키 · `data/` 데이터 · 스냅샷), `logs/`, `ops/`(설치된 운영 스크립트).
- 1분마다: main 머리 커밋이 바뀌었고 그 커밋의 CI가 초록이면 → 세션 스냅샷 → 릴리스 빌드(백엔드 가상환경 + 프론트 build) → `current` 교체 → 백엔드 · 화면 재시작 → 상태 확인(120초).
- 상태 확인 실패 → 이전 릴리스로 되돌리고 그 배포 직전 스냅샷으로 세션도 되돌린 뒤 다시 상태 확인. 같은 커밋은 다시 시도하지 않는다(실패 표시).
- 서버는 LaunchDaemon으로 부팅 때 뜨고, 죽으면 launchd가 다시 띄운다.

### 2-3. 사용자 결정 (D-401~D-404)

| 항목 | 결정 |
|---|---|
| 작업 중 배포 | **기다리지 않고 바로 올린다.** 돌던 크롤링 · 라벨링 · 학습 · 키워드 생성은 "중단됨"이 되고 화면에서 이어서 하기를 눌러야 한다(기존 기능). |
| 상시 실행 | **LaunchDaemon** — 로그인 없이 부팅만 되면 뜬다. 처음 한 번 사용자가 `sudo` 설치 명령을 직접 실행한다. |
| 데이터 보호 | **배포 직전 세션 스냅샷.** `shared/data/sessions`만(큰 수집본 · 모델 파일 제외) 복사하고 최근 5개만 남긴다. 롤백할 때 같이 되돌린다. |
| 알림 | **로그만.** `logs/deploy.log`에 한 줄 JSON으로 남긴다. |

## 3. 검토한 대안 (채택하지 않음)

| 대안 | 이유 |
|---|---|
| 맥미니에 GitHub self-hosted runner 설치 | 공개 저장소라 외부 PR의 코드가 맥미니에서 돌 수 있다. GitHub도 권하지 않는다. |
| 외부 호스팅(Railway · EC2 등) | DCX 2.0은 맥미니 로컬 전용으로 정했다. |
| CI만 두고 배포는 손으로 | 이번처럼 "머지했는데 화면에 없다"가 반복된다. |
| 작업이 끝날 때까지 배포 대기 | 사용자가 "바로 올리고 중단 처리"를 골랐다. |

## 4. 수용 기준

| ID | 기준 |
|---|---|
| AC-01 | PR을 열면 GitHub Actions가 백엔드 테스트 · 프론트 lint · test · build를 돌리고 PR 화면에 결과가 보인다. 키 · 비밀값 없이 초록이 된다. |
| AC-02 | main에 머지된 커밋의 CI가 초록이면, 늦어도 머지 후 (CI 시간 + 5분) 안에 `http://localhost:3400`이 그 커밋을 보여 준다. 화면이나 API에서 지금 커밋을 확인할 수 있다. |
| AC-03 | CI가 빨간 커밋은 배포하지 않는다. 떠 있던 버전은 그대로다. |
| AC-04 | 새 버전이 상태 확인에 실패하면 이전 버전과 그 배포 직전 세션 스냅샷으로 되돌리고, 로그에 이유를 남긴다. 같은 커밋은 다시 시도하지 않는다. |
| AC-05 | 맥미니를 재부팅하면 로그인 없이 화면 · 백엔드 · 배포 타이머가 뜬다. |
| AC-06 | 키(`app.env`)와 데이터(`shared/data`)는 릴리스 폴더 밖에 있어 배포 · 롤백으로 지워지지 않는다. 키는 로그 · 빌드 산출물에 나오지 않는다. |
| AC-07 | 사용자가 띄운 개발 서버(3310 · 3311 · 8310 · 8311)와 internal-app(3000)은 건드리지 않는다. |
| AC-08 | 수동 명령도 있다: 지금 커밋으로 배포 · 직전 버전으로 롤백 · 상태 보기. |

## 5. 제외 범위
- 맥미니 밖에서 접속(터널 · 도메인 · HTTPS) — 지금은 맥미니 브라우저에서 `localhost`로만 본다.
- Slack · 외부 상태 확인 서비스 알림.
- 스테이징 · 여러 환경.
- 데이터 이전(마이그레이션) 도구. 형식이 바뀌는 배포는 지금처럼 코드가 예전 형식을 읽는 방식으로 다룬다.

## 6. 위험

| 위험 | 대응 |
|---|---|
| GitHub API를 토큰 없이 부르면 시간당 60회 제한 → 1분 타이머가 한계에 걸림 | 읽기 전용 fine-grained 토큰(Contents · Actions 읽기)을 `shared/deploy.env`에 두거나, 토큰 없이 쓰면 확인 간격을 2분으로. 설계에서 정한다. |
| 배포 중 백엔드 재시작으로 긴 작업이 중단됨 | 사용자 결정(D-401). 중단 기록은 기존 기능이 남기고 이어서 하기로 재개. |
| 롤백 때 세션 스냅샷 이후 사용자가 저장한 변경이 사라짐 | 롤백은 상태 확인 실패(120초 안) 때만 일어나므로 그 사이 저장은 거의 없다. 롤백 로그에 스냅샷 시각을 남긴다. |
| 백엔드 의존성(scipy · kiwi 등) 설치가 릴리스마다 느림 | `requirements.txt`가 같으면 이전 가상환경을 재사용. 설계에서 정한다. |
| CI(우분투)와 맥미니(macOS) 차이로 CI는 초록인데 맥미니 빌드가 실패 | 맥미니 빌드 실패도 "빌드 실패"로 기록하고 떠 있던 버전을 유지. |
| 지금 손으로 띄운 3400 · 8400 프로세스와 launchd 잡이 충돌 | 설치 단계에서 손으로 띄운 프로세스를 먼저 내린다(사용자 확인 후). |
