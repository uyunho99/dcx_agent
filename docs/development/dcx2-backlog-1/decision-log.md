## 아산병원 데모(2026-10-02) 결정
번호는 6~8단계 기획(D-2xx)과 겹치지 않게 DEMO-로 쓴다. 세션 `s2d08197f2b2d441bada25011d6501e1e`, 서버 8311/3311, 데이터 `data/asan-demo`.

### DEMO-01 키워드는 병원 이름이 없는 일반 원무 Pain Point도 포함 · 확정
- 처음: 1라운드 92개 중 "아산병원"이 들어간 4개만 승인하고, 나머지는 "흔한 단어"로 거절했다. 대신 "아산병원+상황" 14개를 직접 추가했다(타 병원 글 혼입을 막으려는 의도).
- 사용자: "병원이 없어도 그런 거에 대한 페인포인트도 같이 포함해야지. 꼭 아산병원 페인포인트만 참고하는 건 안 좋은 것 같아."
- 변경: 거절한 88개 중 검색어로 쓸 수 있는 50개를 다시 승인했다(unreject). 예: 수납대기시간, 무인수납기오류, 진료비세부내역서발급, 대리발급위임장, 보호자대신수납, 간병인인수인계, 퇴원당일절차, 검사순서착각, 수납완료착각. 남은 38개는 추상적인 표현이라 거절을 유지했다(예: 반복질문눈치, 당일업무완료, 병원이동최소화, 고령환자자립). 승인 합계는 68개.
- 이유: 원무 · 수납 · 서류 · 보호자 역할에서 생기는 혼란은 상급종합병원 공통이다. POC의 Context · Persona는 아산병원 한 곳의 글보다 넓은 VOC에서 더 잘 드러난다.
- 영향: 이미 시작한 수집본 c1에는 처음 18개만 들어 있다. 새로 승인한 50개는 추가 키워드 수집(added-keywords 모드)으로 받는다. 네이버 검색 제한(B-115)이 풀린 뒤 진행한다. 전처리 · 라벨링에서 아산병원 글과 타 병원 글을 구분할 수 있도록 키워드 출처(병원명 포함 여부)를 남겨 둔다.

### DEMO-02 목록(P1)은 네이버 공식 검색 API, 본문(P3)은 기존 코드 · 데모용 빠른 구현 · 확정 (D-094 일부 변경)
- 배경: 검색 화면 수집이 네트워크 단위 검색 제한(B-115)으로 막힘. 키워드당 수백~수천 건 목표(사용자: "수백 수천건을 받자")면 화면 방식은 검색 요청 약 4,600회 → 차단 위험. 사용자가 `NAVER_CLIENT_ID` · `SECRET`을 넣었고 `blog.json` · `cafearticle.json`이 200으로 동작함(2026-10-02).
- 사용자 확인: API는 링크 · 제목 · 요약만 주고 본문은 안 준다 → 목록만 API, 본문은 기존 P3 코드로 링크를 열어 받는다("응 그렇게 진행해줘").
- 방식: 사용자 선택 "B. 데모용 빠른 구현". 별도 worktree(`~/Desktop/dcx_agent-naver-api`, 브랜치 `feature/naver-openapi-list`)에서 Codex 구현 + 테스트 통과 후 데모 서버에 적용. 6~8단계 하네스(product-gate)와 섞이지 않게 분리. main 반영은 나중에 정식 절차로.
- 범위: API 목록 어댑터(키 없으면 화면 방식 유지), B-115 1 · 2 · 3 · 6(간격 덮어쓰기 · 호스트 공유 제한기 · 제한 화면 즉시 감지 · 차단 실패 재시도).
- 영향: 카페 API는 날짜를 주지 않으므로 기간 필터는 본문 수집 뒤(P3) 적용. API 하루 25,000회 한도.
