## B-115 네이버 검색 화면 수집이 "검색 서비스 이용 제한"(HTTP 403)으로 막힘
발견: 2026-10-02 아산병원 데모(세션 `s2d08197f2b2d441bada25011d6501e1e`, 수집본 c1).

**무슨 일이 있었나 (시간 순서)**
1. 키워드 18개 × 블로그 · 카페 2채널로 목록 수집(P1)을 시작. 카페 목록 18건은 모두 성공.
2. 블로그 목록은 첫 1건만 성공하고 이어진 요청이 연속 403 → 20회 연속 차단 규칙(`worker.py` `blocked >= 20`)으로 `paused_blocked`.
3. 블로그만 요청 간격 3초로 재개했지만 1건 성공 후 다시 403 23회 → 다시 `paused_blocked`.
4. 직접 재현: 첫 요청 200(약 40만 바이트) → 10초 뒤 다른 키워드 요청 403(약 2.8만 바이트). 몇 분 쉬면 다시 200이 1건 나오고 곧 403.

**403 화면 내용(요약)**: "검색 서비스 이용이 제한되었습니다. 사용 중인 PC 또는 네트워크에서 검색 서비스를 방해하는 내용이 감지 … 해당 네트워크의 검색을 일시적으로 제한 … 보안 절차를 통과하면 정상 이용". 즉 일시적 오류가 아니라, 네이버가 이 네트워크(맥미니 IP)를 프로그램 검색으로 판정해 `search.naver.com`을 막은 상태. 보안 절차(사람 확인)는 자동으로 통과시키지 않는다(우회 금지).

**원인으로 보이는 것**
- (a) 요청 간격 0초로 실행됨 — 버그. D-094는 네이버 요청 간격 1초인데, 크롤 설정에서 `perChannel`에 `max_per_keyword`만 넣어도 `Limits` 모델 기본값 `min_interval_s=0`이 함께 저장돼 네이버 기본 1초(`control.py` 349행 기본값)를 덮어씀. 데모에서도 상태 화면이 `min_interval_s: {naver_blog: 0, naver_cafe: 0}`으로 표시됨.
- (b) 블로그 · 카페가 같은 호스트(`search.naver.com`)를 쓰는데, 채널별로 따로 동시성 4 · 간격을 적용함 → 호스트 기준으로는 두 채널 요청이 합쳐져 짧은 시간에 몰림.
- (c) 같은 형태 검색어("아산병원○○")를 짧은 간격으로 연달아 던지는 패턴 자체가 403 화면의 "특정 단어를 반복적으로 대량 입력" 판정과 맞음.
- (d) 한 번 제한되면 간격을 늘려도 바로 풀리지 않음(재개 후 1건 성공 → 다시 차단). 제한 해제 시간은 알 수 없음.

**할 일(제안)**
1. 버그 수정: `perChannel` 일부만 지정해도 지정하지 않은 값(`min_interval_s`, `concurrency`)은 채널 기본값을 유지. 테스트 추가.
2. 호스트 단위 속도 제한: `search.naver.com`을 쓰는 채널(블로그 · 카페 목록)이 하나의 제한기를 공유. 기본은 동시성 1, 간격 수 초 + 무작위 지터.
3. 차단 감지 개선: 403 화면 문구("검색 서비스 이용이 제한")를 인식해 `blocked_by_naver`로 따로 표시하고, 연속 20회까지 두드리지 말고 첫 감지에서 바로 해당 호스트 전체를 멈춤(같은 호스트의 다른 채널 포함). 화면에 "네이버가 이 네트워크의 검색을 일시 제한했습니다. 시간이 지난 뒤 이어받기"라고 안내.
4. 자동 재개 대기: 일시 정지 후 일정 시간(예: 30분 → 60분) 뒤 1건만 시험 요청하고, 성공할 때만 이어받기.
5. 목록(P1) 단계 부분 완료 허용: 지금 `finish-partial`(D-097)은 상세(P3) 단계에서만 동작해서, 목록 단계에서 한 채널이 차단되면 다른 채널(카페 목록 18건 완료)까지 다음 단계로 못 넘어감. 데모에서 `finish-partial` → "No paused detail channels", 상세 시작 → "Finish list collection before starting detail". 차단된 채널의 남은 목록 작업을 건너뛰고 받은 만큼으로 게이트로 가는 경로 필요.
6. 차단 중 소진된 목록 작업 재시도: 차단되는 동안 블로그 목록 작업 14개가 재시도 3회를 다 써서 `failed`로 굳음. 차단이 풀린 뒤(2026-10-02 01:0x, 시험 요청 200) 15초 간격으로 재개해도 이 14개는 다시 시도되지 않고 목록 단계가 `done`으로 끝남(블로그 18개 중 4개만 수집). 차단(`AdapterBlocked`)으로 실패한 작업은 시도 횟수에서 빼거나, 재개 시 다시 대기열에 넣어야 함.
7. 대체 경로 검토: 사용자가 `.env`에 `NAVER_CLIENT_ID` · `NAVER_CLIENT_SECRET`을 넣음(2026-10-02). D-094 당시에는 "키를 받을 수 없음"이 전제였으므로, 이 키로 네이버 검색 API(블로그 · 카페 목록)를 시험함 → 2026-10-02 `blog.json` · `cafearticle.json` 모두 200("아산병원 수납" 블로그 24,706건 · 카페 7,175건). 지금 v2 코드에는 공식 검색 API 어댑터가 없음(D-094로 만들지 않음, `app/services/naver.py`는 1.0 시절 키워드 점수용으로 v2 수집에서 안 씀). 따라서 목록(P1)은 API, 본문은 지금처럼 화면으로 받는 방식을 D-094 개정안으로 올린다.

관련: D-094, `app/crawl/adapters/naver_common.py`(`request`, `list_page`), `app/routers/crawl_v2.py`(`Limits`), `app/crawl/control.py`(349행 기본 간격), `app/crawl/worker.py`(171~174행 차단 카운트).

### 구현 메모(2026-10-02)
- 네이버 키가 설정되면 블로그·카페 목록은 공식 검색 API를 사용한다. 정확도순·날짜순을 각각 start 901까지 수집하고 URL/키워드 중복을 제거하며, 키워드별 상한은 두 정렬의 고유 URL 합계에 적용한다. 키가 없거나 `x`이면 기존 HTML 경로를 유지한다.
- HTML 검색은 호스트 공유 제한기(동시성 1, 두 채널 간격의 최댓값), API는 별도 제한기(동시성 2, 0.1초)를 사용한다. 검색 제한 문구는 HTTP 상태와 무관하게 즉시 두 채널을 일시 정지한다.
- 일부 `perChannel` 설정은 명시한 필드만 저장한다. 차단은 목록·상세 재시도 횟수를 소진하지 않으며, 재개 시 기존 `AdapterBlocked` 목록 실패도 다시 대기열에 넣는다.
- 상세 수집 경로는 유지하고 카페 상세 날짜 필터를 검증했다. `/integrations`에 네이버 키 설정 상태를 추가했으며, API·페이지네이션·중복·차단·복구 회귀 테스트는 외부 통신 없이 실행한다.
