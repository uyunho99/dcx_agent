# 키워드 R2 잠금 · R1→R3 · r3.v3 / r4.v3 — 설계

기준: origin/main `a63ffa9`. 기획: `01-brainstorm.md`(승인).

## 1. 동작 원칙
- "잠긴 라운드" 집합 하나로 R2를 끈다. 서버 설정 `keyword_locked_rounds`(기본 `[2]`, 환경변수 `KEYWORD_LOCKED_ROUNDS`)로 두고, 빈 목록이면 지금과 똑같이 동작한다(되돌리기 = 설정값 하나).
- 잠긴 라운드 = "건너뛰는 라운드". 번호 체계(1~4), 저장 구조, 화면 단계 표시는 그대로다.
- "이전 라운드" = 잠기지 않은 바로 앞 번호. R3의 이전 라운드는 R1이다.

## 2. 서버 (backend/app/keywords/rounds.py, config.py, routers/keywords_v2.py)
| 위치 | 지금 | 바꾼 뒤 |
|---|---|---|
| `config.Settings` | — | `keyword_locked_rounds: list[int] = [2]` |
| `rounds.locked(n)` / `rounds.previous_round(n)` (신규, 순수 함수) | — | 잠금 여부 · 잠기지 않은 앞 라운드(없으면 None) |
| `_number(n)` 이후 잠금 검사 (start_round · commit_round) | — | 잠긴 라운드면 `StoreError('R2는 사용하지 않습니다. R1 다음은 R3입니다', 409, 'round_locked')`. 생성 · 다시 생성 · 확정 모두 거절. 작업은 만들지 않는다 |
| `_order(data, n)` | 1..n-1 모두 확정 · 재생성 불필요여야 함 | 잠긴 라운드는 검사에서 제외 |
| `_all_keywords(data, exclude_round)` (중복 판정 원천) | 모든 라운드의 keywords 포함 | 잠긴 라운드 중 **확정되지 않은** 라운드의 keywords는 제외. 확정된 R2(예전 세션)는 포함 |
| `commit_round` 끝의 커버리지 시작 | `if n == 2` | `if n == previous_round(3)` (잠금 기본값에서 R1, 잠금 없음이면 R2) |
| `start_round`의 R3 커버리지 대기 검사 | 그대로 | 그대로 (R3 생성 시 커버리지 loading이면 409) |
| GET `/keywords/{sid}` 응답 | `keywordRounds` 전부 | 잠긴 라운드 중 확정되지 않은 것은 응답에서 뺀다(저장 파일은 그대로). 버전 조회(`?version=`)도 같은 함수 사용 |
| GET `/keywords/{sid}/rounds/2` | 저장값 반환 | 변경 없음(화면은 부르지 않음) |
| `PROMPT_VERSION` | `{3: r3.v2, 4: r4.v2}` | `{3: r3.v3, 4: r4.v3}`. r2.v2 파일은 남긴다(잠금 해제 시 사용) |

R1 재확정으로 뒤 라운드에 `needsRegeneration`이 붙는 기존 동작은 그대로다. R2에 붙어도 `_order`가 잠긴 라운드를 건너뛰므로 영향이 없다.

## 3. 지시문 (backend/app/keywords/prompts/r3.v3.md, r4.v3.md 신규)
공통: 형태 규칙 · 분류 · 출력 절은 r3.v2/r4.v2(= r1.v3 형태 규칙 포함)와 **글자 그대로 같다**. 바뀌는 곳은 "임무"와 "사고 절차" 절, 그리고 R4에 추가되는 입력 블록뿐이다. 자리표시자는 기존 `values`에 있는 것만 쓴다(새 키 없음).

### r3.v3 — 수렴 + 약간 균형
- 임무 문장: "이 제품군 안에서 승인 키워드를 비슷한 주제로 모아 그 주제를 깊게 채우고, 부족한 축은 보조로 보완한다."
- 사고 절차:
  1. 승인 키워드와 사용자가 직접 추가 · 이동한 키워드를 의미가 비슷한 주제 묶음으로 나눈다(예: 겨울 냉기 · 결로 / 마을 관계 거리 / 귀촌 후회 · 역귀촌). 묶음은 출력하지 않는다.
  2. 승인이 많거나 직접 추가 · 이동이 있는 주제를 우선한다. 같은 상황 안에서 아직 없는 다른 사물 · 현상 · 행동 단어로 채운다.
  3. 앞말(맥락어)만 바꾼 변형은 같은 단어로 본다. 예: 시골집외풍 · 전원외풍 · 농가외풍은 하나만 쓴다. 기존 승인 키워드의 맥락어만 바꾼 단어도 만들지 않는다.
  4. 생성량의 약 7할은 주제 수렴(2단계)에, 약 3할은 축 분포에서 가장 적은 축 보완에 쓴다. 커버리지 신호가 있으면 이 3할에 우선 반영한다. 커버리지가 없으면 검색량을 추정하지 않는다.
  5. 거절 사유에 해당하는 표현과 과거 0건 키워드의 반복을 피한다.
- 입력 블록(축 분포 · 거절 신호 · 원하는 방향 · 커버리지 · 과거 0건 · 기존 승인)은 r3.v2와 같다.

### r4.v3 — 마지막 발산 · 정리
- 임무 문장: "이 제품군 안에서 지금까지 다루지 않은 상황을 마지막으로 발산하고 목록을 정리한다."
- 사고 절차:
  1. 승인 키워드를 주제로 훑어 이미 다룬 상황을 파악하고, 아직 비어 있는 상황 · 사람 · 시점을 찾는다.
  2. SCAMPER 대체 · 결합 · 응용으로 다른 사물 · 조건 · 상황의 접점을 찾는다.
  3. SCAMPER 역발상 · 제거와 극단 사용자(빈도 · 조건 · 제약)로 당연하게 여긴 전제가 없거나 뒤집힌 상황을 찾는다. 부정 공간의 대체 · 전환 · 이탈도 본다.
  4. 기존 주제의 인접어와 앞말(맥락어)만 바꾼 변형은 만들지 않는다. 새 단어마다 기존 승인 키워드와 다른 상황이어야 한다.
  5. 정리: 결과가 세 축에 고르게 걸치도록 마무리하고, 거절 사유에 해당하는 표현을 피한다.
- 입력 블록: 기존 승인 키워드 + 축 분포 + 거절 신호(r3과 같은 자리표시자 `{category_distribution}`, `{rejection_signals}`).

## 4. 화면 로직 (모양 그대로)
| 위치 | 지금 | 바꾼 뒤 |
|---|---|---|
| `lib/logic/roundUi.ts` | `directionRound = min(round+1, 4)` | 잠기지 않은 다음 라운드(`nextRound(round)`: 1→3, 3→4, 4→4). `LOCKED_ROUNDS = [2]` 상수와 `nextRound` · `prevRound` 함수 추가 |
| `keywords/page.tsx` `next()` | `generate(round + 1, …)` | `generate(nextRound(round), …)` |
| `page.tsx` `nextRound` 데이터 (`keywordRounds[round+1]`) | round+1 | `keywordRounds[nextRound(round)]` |
| `page.tsx` 다음 버튼 커버리지 막음 | `round === 2 && coverageLoading` | `nextRound(round) === 3 && coverageLoading` |
| `page.tsx` 커버리지 대기 안내 (`round === 2 \|\| round === 3`) | 2 · 3 | `prevRound(3)` · 3 |
| `page.tsx` 커버리지 카드 표시 조건 · h1 크기 | `keywordRounds['2']?.committed` | `keywordRounds[String(prevRound(3))]?.committed` |
| 커버리지 카드 배지 문구 | "R2 확정 후 계산" | "R{prevRound(3)} 확정 후 계산" → 지금은 "R1 확정 후 계산". **화면 글자가 바뀌는 유일한 곳**(계산 시점이 실제로 R1 확정으로 바뀌어서) |
| 처음 여는 라운드 · 선택 목록 · 단계 표시 | `keywordRounds` 키 기준 | 변경 없음. 서버가 미확정 R2를 응답에서 빼므로 세라젬은 R1로 열리고 선택 목록에 R2가 없다. 단계 표시의 R2 칸은 "다가올 단계" |

`plan-design-review` 미적용 사유: 레이아웃 · 컴포넌트 · 상태 표현이 바뀌지 않는다(바뀌는 것은 버튼이 부르는 라운드 번호와 표시 조건, 배지 숫자 하나). 브라우저 QA로 화면 동일성을 확인한다.

## 5. 데이터 · 호환
- 저장 파일 이전 없음. 세라젬의 미확정 R2 기록은 파일에 남지만 응답 · 중복 판정 · 순서 검사에서 무시된다.
- R2를 확정한 예전 세션: 응답 · 승인 목록 · 중복 판정 모두 그대로. R3/R4 진행 가능.
- R2 작업이 실행 중인 상태에서 배포·재시작되면 기존 `recover_interrupted`가 failed로 표시한다. 응답에서는 미확정이라 보이지 않는다.
- 잠금 해제(`KEYWORD_LOCKED_ROUNDS=[]`) 시: 응답 · 순서 · 커버리지 시작이 예전(R2 확정)으로 돌아간다. 화면 상수 `LOCKED_ROUNDS`도 함께 바꿔야 한다(한계: 화면은 서버 설정을 읽지 않는다 — 이번 범위에서는 상수로 충분).

## 6. 실패 상태
| 상황 | 결과 |
|---|---|
| R2 생성 · 다시 생성 · 확정 요청 | 409 `round_locked`, 안내 문구. 상태 변화 없음 |

| R3 · R4 생성 실패 | 기존 실패 배너 · 다시 생성 그대로 |

## 7. 권한
변경 없음(로컬 단일 사용자, 기존 쓰기 가능 버전 검사 그대로).

## 8. 테스트 방향
- 백엔드: 잠금 거절(R2 start · regenerate · commit), R1→R3 순서, 미확정 R2 단어가 R3 중복 판정에서 빠짐, GET 응답에서 미확정 R2 제외 · 확정 R2 유지, R1 확정 시 커버리지 시작, 잠금 해제 설정에서 예전 동작, r3.v3 · r4.v3 지시문 문구 · 형태 규칙 포함.
- 기존 테스트 중 R2를 거치는 것(`through(client, 2)` 등)은 새 흐름(R1→R3)으로 고치거나, R2 고유 동작 검증은 잠금 해제 설정에서 돌린다. 테스트를 지우지 않는다.
- 프런트: `roundUi` 단위 테스트(`nextRound` · `prevRound` · `directionRound`), 키워드 화면 테스트가 있으면 다음 라운드 호출 번호 확인.
- 브라우저 QA: 가짜 LLM 서버에서 새 세션 R1 저장 → 다음 라운드 생성 → R3, 세라젬 형태(미확정 R2) 세션이 R1로 열림, 화면 비교 스크린샷.
- 실제 LLM(AC9): 세라젬 세션 복사본에서 R3 생성 후 R2와 사례 비교(보고용).
