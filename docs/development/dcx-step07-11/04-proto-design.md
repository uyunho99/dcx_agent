# 04 · Design — 인터랙티브 프로토타입

실행 ID `dcx-step07-11` · base `65e5b14` · 2026-09-18

`mockup/README.md`가 남긴 숙제를 받는다 — *"정적 아트보드다. 인터랙션은 별도 세션에서 부여한다 (클릭·입력·단계 전환)."*

---

## 1. 무엇을 만드는가

15개 정적 아트보드를 **내부 리뷰·의사결정용 클릭형 프로토타입**으로 만든다. 단일 HTML 하나를 빌드해 Artifact로 게시하고, 링크를 받은 사람들이 화면을 넘겨보며 미결 항목에 결론을 남긴다.

제품 코드가 아니다. `frontend/`는 건드리지 않는다.

### 용도가 범위를 정한다

용도는 **내부 리뷰**다. 사용자 테스트도 개발 핸드오프도 아니다. 그래서 두 가지가 따라온다.

- 화면이 *계산하는 척*을 하지 않는다. 숫자는 지금처럼 고정값으로 둔다.
- 리뷰가 결론을 내고 끝나야 한다. 그래서 미결 항목과 메모가 이 프로토타입의 중심이다.

### 왜 미결 항목이 중심인가

답이 필요한 항목이 **16개**, 12개 화면에 흩어져 있다. 리뷰 회의의 실제 안건이 이미 목업 안에 박혀 있는데, 지금은 화면을 하나씩 열어야만 보인다. 한곳에 모으는 것이 이 작업의 절반이다.

수집 단위는 `.tag.open` 클래스다. 라벨이 네 가지로 갈린다.

| 라벨 | 개수 |
|---|---|
| `미결` | 13 |
| `확인 필요` | 1 |
| `잠정` | 1 |
| `경고` | 1 |

`build.mjs`의 범례가 `미결`을 "답이 필요한 것"으로 정의하는데, 나머지 셋도 같은 족속이라 함께 모은다. 반대로 `치환`(35) · `신설`(28) · `유지`(23) 86개는 모으지 않는다 — 그건 결정 대상이 아니라 보고다.

`Evidence` · `Declare` · `ContextMap` 세 화면은 열린 항목이 하나도 없다. 오버레이는 이 셋을 빈 그룹으로 표시한다 — 신규 구현 화면인데 답이 다 나와 있다는 사실 자체가 리뷰에서 확인할 값어치가 있다.

## 2. 구조

기존 파이프라인에 타깃 하나를 추가한다. 정적 아트보드는 그대로 둔다.

```
parts/*.body.html  ─┬─→ build.mjs     → project/*.dc.html   (정적 아트보드 · 기존)
_shell.css          ├─→ preview.mjs   → preview.html        (스택 뷰 · 기존)
                    └─→ proto.mjs     → proto.html          (인터랙티브 · 신규)
```

### shell.mjs 추출

`build.mjs`의 `STEPS` · `ORDER` · `sidebar()` · `topbar()` · `meta()`를 `shell.mjs`로 옮기고 `build.mjs`와 `proto.mjs`가 함께 import한다.

사이드바 정의가 두 벌이 되면 반드시 어긋난다. 15단계 순서와 이름은 한 곳에서만 정의된다.

`build.mjs`의 동작은 바뀌지 않는다. import 경로만 바뀐다. 기존 `project/*.dc.html` 산출물이 바이트 단위로 동일해야 한다 — 이것이 이 리팩터링의 합격 조건이다.

### 단일 셸 + 템플릿

`proto.html`은 셸(상단바·사이드바·메인 프레임)을 **하나만** 두고, 15개 화면의 `MAIN`·`CHAT`·`ANN`을 `<template data-screen="Clustering">`에 담는다.

`preview.html`처럼 아트보드를 15벌 넣지 않는다. 그러면 636KB가 되고, 무엇보다 **셸이 15개가 되어 화면 전환에서 상단바·사이드바가 살아남지 못한다.**

## 3. 인터랙션

### 3-1. 셸과 라우팅

| 동작 | 결과 |
|---|---|
| 사이드바 항목 클릭 | 해당 화면으로 교체 · `cur`/`done` 표시 갱신 |
| `←` `→` | 순서대로 이동 |
| URL 해시 `#Clustering` | 특정 화면 직접 열기 |
| 상단 진행 바 | 15단계 중 현재 위치 |

화면 교체는 `<template>` 복제 후 스왑이다. 화면별 위젯 상태(어떤 토글이 켜져 있었는지)는 **유지한다** — 앞뒤로 오가며 비교하는 것이 리뷰의 기본 동작이다.

### 3-2. 주석 레이어 토글

`설명 모드` 버튼 하나로 핀 **173개**와 하단 `1.0 대비 변경점` 스트립 **15개**를 동시에 껐다 켠다.

- 기본값 **켜짐** — 설명용 장표이므로
- 끄면 제품 화면처럼 보인다

구현은 `.art`에 `data-ann="off"` 하나를 붙이고 CSS로 숨긴다. DOM을 건드리지 않는다.

### 3-3. 선별 위젯

새로 설계하지 않는다. **이미 그려진 것만** 살린다.

| 대상 | 개수 | 동작 |
|---|---|---|
| `.seg` 세그 토글 | 22 (12화면) | 위임 핸들러 1개 — 클릭한 항목으로 `.on` 이동 |
| 표 행 | 다수 | 클릭 시 하이라이트 (선택 상태 시각화) |

**전부 순수 시각 상태 변경이다. 숫자를 재계산하는 위젯은 하나도 없다.**

`허용 오류율` 슬라이더(α → 기준선·문장 수·시간 연동)를 후보에 올렸다가 뺐다. 목업이 계산하는 척을 하면 고정된 가짜 숫자가 근거처럼 읽힌다. 리뷰에서 α는 *값*을 만져볼 대상이 아니라 *미결 항목*으로 논의할 대상이다 (`Training` 화면의 미결 — "α 기본값 · 캘리브레이션 표본 추출").

### 3-4. 미결 오버레이

`미결 16` 버튼 → 오버레이. 12개 화면에 흩어진 항목이 화면별로 묶여 한 목록에 나온다.

항목 하나가 갖는 것:

- **라벨** — `미결` / `확인 필요` / `잠정` / `경고` 중 무엇인지
- **원문** — `.tag.open`을 담은 ANN 항목의 텍스트 전체를 빌드 시점에 파싱해 가져온다. 라벨 뒤에 `<b>` 강조가 섞여 있으므로 태그를 제거한 평문으로 뽑는다
- **상태** — `미정` / `결정` / `보류`
- **메모** — 누가 언제 무엇을 적었는지
- **이동** — 클릭하면 해당 화면의 해당 핀 위치로 스크롤

`보류`가 3번째 상태로 있는 이유는 "오늘 안 정한다"를 명시적으로 남기기 위해서다. 이 칸이 없으면 다음 회의에서 같은 항목을 처음부터 다시 연다.

## 4. 리뷰 메모 — 저장 구조

`db` · `user` capability를 쓴다. 같은 링크를 연 모든 사람이 같은 목록을 본다.

```
issues/{issue_id}
  → { screen, seq, status, updatedAt, updatedBy }

issues/{issue_id}/notes/{note_id}
  → { text, authorId, createdAt }
```

### issue_id

`Clustering-1` 형태 — **화면명 + 그 화면 안에서의 등장 순서**. 빌드 시점에 결정된다.

목업을 재빌드해도 항목 순서가 그대로면 메모가 따라온다. 순서가 바뀌면 끊긴다. 그건 감수한다 — 대안인 본문 해시는 오타 수정 한 번에 끊기고, 리뷰 중에 문구는 자주 고쳐진다.

### 작성자

`user.id()`가 준 불투명 id만 저장한다. 표시할 때마다 `user.profiles()`로 이름을 조회한다.

이름을 문서에 저장하면 안 된다. 사람마다 다르게 보이고, 한 번 쓰면 그 시점 값으로 고정된다.

### 권한

| 보는 사람 | 결과 |
|---|---|
| 조직 구성원 · 편집 가능 | 메모 작성 · 상태 변경 |
| 조직 구성원 · 보기 전용 | 기존 메모 읽기만 |
| 링크만 받은 외부인 | `use("db")`가 `null` — 읽기 전용 렌더 |

`null`이 떨어지는 경우를 정상 경로로 다룬다. 메모 UI를 숨기고 프로토타입 자체는 그대로 돈다. 미결 오버레이도 원문은 보인다 — 그건 페이지에 박혀 있는 정적 데이터다.

`db`는 공유 상태이고, 읽어온 내용은 **신뢰할 수 없는 입력**이다. 메모 텍스트는 `textContent`로만 넣는다. `innerHTML` 금지.

## 5. 배포

Artifact로 게시한다.

| 파일 | 크기 | 비고 |
|---|---|---|
| `proto.html` | ~350KB | 15화면 템플릿 + 셸 + 스크립트 |
| Pretendard 4종 woff2 | 3.4MB | supporting files |
| `person-a-logo.png` | 700KB | supporting files |

외부 CDN은 CSP로 막혀 있어 폰트를 같은 origin에서 서빙하는 것 외에 다른 길이 없다. 제한(페이지 16MB · 바이너리 각 15MB · 총 64MB)에는 여유가 크다.

로컬에도 `mockup/proto.html`이 남아 레포에서 바로 열어볼 수 있다. 다만 로컬에서는 `claude.use()`가 `null`이라 메모 기능 없이 프로토타입만 돈다 — 이것이 §4의 `null` 경로가 반드시 동작해야 하는 두 번째 이유다.

## 6. 디자인 시스템

`_shell.css`(Person A 토큰)를 그대로 쓴다. 신규 UI는 **셸 크롬 3개**뿐이다 — 설명 모드 토글, 미결 버튼, 미결 오버레이.

기존 준수 상태를 유지한다.

- 원시 hex·px 리터럴 0건 — 신규 UI도 `var(--토큰)`만 쓴다
- uppercase 없음 · 12px 미만 없음 · 정적 카드 그림자 없음
- 액션은 `--action #0a73b5` · 브랜드 블루로 버튼을 채우지 않는다

규칙 문서는 `DESIGN.persona.md`.

## 7. 범위 밖

의도적으로 뺀 것을 적는다. 나중에 "왜 없지"가 나오지 않게.

| 뺀 것 | 이유 |
|---|---|
| 화면을 가로지르는 세션 상태 (CL0 선택이 08·09·10으로 전파) | 핸드오프용이지 리뷰용이 아니다 |
| 입력 폼 · 저장 · 잡 진행 시뮬레이션 | 리뷰에 필요 없다 |
| α 슬라이더 등 숫자 연동 위젯 | §3-3 |
| 나머지 위젯 전부의 동작화 | 논쟁이 벌어지지 않는 지점이다 |
| Liquid Glass 변형 | 동결 상태 유지 |
| 인증 | 앱에 없다. Artifact 권한으로 갈음한다 |

## 8. 성공 기준

1. `node build.mjs`의 산출물이 리팩터링 전과 **바이트 단위로 동일**하다
2. 15화면을 사이드바·키보드·URL 해시 세 경로로 모두 오갈 수 있고, 전환 후에도 셸과 위젯 상태가 살아 있다
3. `설명 모드` 끄기 한 번으로 핀 173개와 ANN 스트립 15개가 함께 사라진다
4. 열린 항목 16개가 한 목록에 모이고, 클릭하면 원래 자리로 이동한다. 항목이 없는 화면 3개는 빈 그룹으로 나온다
5. 두 사람이 같은 링크에서 메모를 남기면 서로에게 보인다
6. `claude.use()`가 `null`인 환경(로컬 파일 열기)에서도 1~4가 그대로 동작한다
