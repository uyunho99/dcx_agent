# GPT(Codex) 판정 동시 처리 — 기획

## 문제
- 4단계 GPT 판정은 글 20건을 한 묶음으로 Codex 에이전트 1개에 보내고, 끝나야 다음 묶음을 보낸다(`judge.run_worker` → `gpt.judge_batch` → `run_many([task])`).
- 운영 실측(2026-10-03, 세라젬): 분당 약 20건, 87,143건에 약 7일.
- `LABEL_CONCURRENCY`(기본 4)는 `run_many`에 작업이 1개뿐이라 효과가 없다.

## 결정 (사용자, 2026-10-03) — D-343
- **C. 묶음 여러 개를 동시에 처리, 운영은 동시 20개.** 묶음 크기(20)는 그대로(품질 영향 없음).

## 대안
| 안 | 설명 | 판단 |
|---|---|---|
| A. 그대로 | 7일 | 거절 |
| B. 묶음 크기 50 | 설정만, 약 2배 · 긴 입력으로 시간 초과 · 품질 위험 | 거절 |
| C. 동시 묶음 (선택) | 코드 수정, 동시 N배 | 선택 |

## 동작 (예시)
- `LABEL_CONCURRENCY=20`: 워커가 400건(20묶음)을 임대해 Codex 20개를 동시에 띄운다. 묶음마다 끝나는 대로 결과를 저장하고, 20개가 다 끝나면 다음 400건.
- 묶음 3개가 사용량 한도에 걸리면: 나머지 17묶음 결과는 저장, 한도 묶음은 임대 해제, 판정은 기존처럼 "사용량 한도" 일시정지 → 나중에 "이어서 진행".
- 묶음 1개가 응답 형식 오류면: 그 묶음 글만 기존처럼 실패 처리(재시도 · 검수 큐), 나머지는 정상.

## 수용 기준
- AC1: GPT 판정 워커가 한 번에 `LABEL_CONCURRENCY`개 묶음(각 `LABEL_BATCH_SIZE`건)을 동시에 처리한다(Codex · API · fake 공통).
- AC2: 동시 묶음 중 일부가 일시정지 사유(한도 · 백엔드 실패)여도 성공한 묶음 결과는 저장되고, 실패 묶음은 기존 규칙대로(한도 → 임대 해제 · 일시정지 / 백엔드 실패 → 실패 기록 · 일시정지 / 형식 오류 → 해당 글 실패).
- AC3: 동시 처리 중에도 하트비트가 끊기지 않아 다른 워커가 임대를 회수하지 않는다.
- AC4: 같은 글이 두 번 판정되거나 결과가 섞이지 않는다(묶음별 run ID · 저장 결과 일치).
- AC5: `LABEL_CONCURRENCY=1`이면 지금과 같은 동작. Jev 판정 경로는 변경 없음.
- AC6: 남은 시간 추정이 동시 처리 속도를 반영한다(최근 처리량 기반 — 기존 방식 유지 확인).
- AC7: 백엔드 pytest · 프런트 lint · build · test 통과.

## 제외 범위
- 묶음 크기 변경, Codex 프로필 · 모델 변경, Jev 동시성.

## 위험
- Codex 플랜 한도에 빨리 도달 → 기존 한도 일시정지 흐름으로 처리, 사용자가 동시 수를 낮출 수 있음(설정만).
- 맥미니 부하(Codex 프로세스 20개) → 운영 값은 설정으로 조절.
