### D-201 기획 · 설계는 6~8단계를 한 번에, 구현은 3번으로 나눈다 · 확정 (사용자)

- 운영: 이 실행(`dcx2-stage6-8`)의 `01-brainstorm.md` · `02-design.md`가 6~8단계 전체를 다룬다. 구현은 ① 6단계 구획(+6.5 · 6-A/B/C 화면) ② 7단계 근거 탐색(+Evidence Package) ③ 8단계 서술(+insight-chat) 세 묶음으로 나눈다.
- 이유: 구간 계약(`stage_6.json` · Evidence Package)이 세 묶음을 잇기 때문에 설계를 한 번에 해야 계약이 어긋나지 않는다. 구현 · 리뷰 · QA는 묶음 단위가 작아야 되돌리기 쉽다.
- 미정: 묶음 ②·③의 하네스 실행 운영(이 실행의 승인된 01 · 02를 참조하는 별도 실행 vs 한 실행 안의 단계별 마일스톤)은 계획 단계에서 정한다.

### D-202 Pinecone 전제는 로컬 벡터 검색으로 치환 · 확정 (D-121 승계) · 기획안과의 차이
- 기획안은 "Pinecone metadata · 6.5단계 적재 · filter 3키"를 전제한다. 3~5단계 D-121에서 Pinecone을 제거하고 로컬 벡터 검색 하나로 확정했다.
- 영향: 문서 metadata는 로컬 저장소에 두고 filter는 로컬 마스크로 구현한다. 6.5단계는 "Core dims 추출"만 남는다. 기획안 미결 "조합 희소성 저장소(Pinecone vs 그래프 DB)"는 로컬 테이블로 닫힌다.

### D-203 backlog-1과의 파일 겹침은 없음 · 확인
- backlog-1이 PR #4로 main에 머지됨. 6~8단계는 main(`b36b01f`)에서 출발하므로 `StepBar.tsx` · `pipeline/layout.tsx` · `context/versions.py` · `context/stale.py` 변경을 그대로 이어받는다.

### D-204 6단계는 1.0 방법 하나만 · 서브 K-means 안 함 · 확정 (사용자) · 기획안과의 차이
- 사용자: "아니 그냥 1.0으로만 할거야. 서브 k-means는 안할거야."
- 기획안 2절의 "두 갈래 병행(기존 ∥ 수정)"을 하지 않는다. L1 Cluster = Ward 덴드로그램 + 실루엣 · Elbow로 k 진단 → K-means + TF-IDF, L2 Persona = 명사 동시출현 네트워크 모듈성 분할, L3 Context = Persona 안 gensim LDA(topic_num 2~10, Coherence↑ · Perplexity↓).
- 따라오는 변경:
  - `primary_method` 토글 · 두 갈래 비교(ARI · NMI · 최대겹침 매칭표 "1.0 재현성") 없음. Stability는 재표집 ARI만.
  - Importance는 LDA "토픽일 확률"을 그대로 쓴다(기획안의 "센트로이드 거리를 확률로 바꾸기"는 불필요).
  - 3단계 형태소 토큰(kiwi) 경로가 6단계 필수 입력이 된다.
  - LDA에는 센트로이드가 없으므로 `dist_centroid` · 밴드(P50/P90) · 레이더의 "Context 센트로이드"를 다시 정의해야 한다 → 설계에서 정함.
  - 1.0 L2의 "Desire 유사한 것 통합"은 클러스터를 가로지르므로, 기획안 닫힌 항목 "Persona는 클러스터의 자식"과 충돌 → 질문으로 정함.

### D-205 L1 Cluster 입력은 3단계 Voyage 임베딩 · 확정 (사용자)
- 3단계 voyage-4 1024차원 벡터를 재사용해 Ward 덴드로그램(표본) · 실루엣 · Elbow로 k를 진단하고 K-means를 돌린다. 클러스터 키워드는 형태소 토큰 c-TF-IDF.
- 이유: 표현이 다르고 뜻이 같은 글("워치랑 이어폰 둘 다 챙기기 귀찮다" / "기기 두 개 차는 게 번거롭다")을 같은 Touch Point로 묶기 위해. AS-IS 코드도 같은 방식.
- L2 네트워크 · L3 LDA는 형태소 토큰을 쓴다(D-204).

### D-206 클러스터를 가로지르는 Persona 통합은 제안 배지만 · 확정 (사용자) · 1.0과의 차이
- 6-B에 "⇄ CL2-P1과 Desire 유사 0.86" 배지만 보이고 통합은 실행하지 않는다. Persona는 클러스터의 자식(클러스터당 2~3개)이고 ID `CL0-P1` 체계를 유지한다.
- 이유: 통합하면 ID · 7단계 filter · SNAGraph 트리 · 되돌리기가 모두 복잡해진다. 통합은 merge/split/move와 함께 포스트 MVP(기획안 닫힌 항목). 페르소나를 가로지르는 묶음은 8-E 인사이트가 맡는다.

### D-207 6.5 Core dims 추출은 표본 + 지연 추출 · 확정 (사용자) · 기획안과의 차이
- 6.5단계: Context마다 토픽 확률 상위 Core 최대 100건만 5-Dim 추출 → `dominant_constraint` · 조합 공출현 빈도(combo_rarity 기준)를 이 표본으로 계산한다.
- 7단계: 검색 후보로 올라온 Core 중 dims가 없는 문서는 2차 프롬프트가 dims를 함께 추출하고 문서 단위로 캐시한다. 표본 밖 문서의 combo_rarity는 이때 표본 빈도표로 계산한다.
- 이유: Core 전량(31만 건 중 30%면 약 9만 건)은 호출 수천~수만 회로 시간 · 비용이 데이터 규모에 비례한다. 표본 크기는 Context 수 × 100으로 고정돼 예측 가능하다.
- 기획안과의 차이: 기획안은 "Core 원문 전체 추출 → 적재 시 metadata". 이번에는 표본 + 검색 후보만.

### D-208 8-E · 8-F는 구조화 화면 + 채팅 수정 · 확정 (사용자) · 기획안과의 차이
- 8-E(인사이트 카드 · 레이더 · Opportunity 막대) · 8-F(PERSONA · Pain Points · JOURNEY AS-IS/TO-BE · 4D-CX)를 버튼으로 한 번 생성해 고정 레이아웃으로 보여 준다. 오른쪽 채팅에서 "인사이트 2를 두 개로 나눠줘" 같은 요청으로 고치면 수정본이 저장된다(MODIFIED_DATA 역할).
- 기획안과의 차이: 자유 편집 캔버스 · 채팅↔캔버스 양방향 동기화는 하지 않는다.

### D-209 새 버전에서 6단계 확정값은 처음부터 · 확정 (사용자)
- "4단계부터 다시" 등으로 6단계를 다시 돌리면 클러스터 이름 · Desire · Goal · Context 이름은 빈칸에서 다시 확정한다. 이전 버전 값을 겹침 매칭으로 옮겨 오지 않는다. 이전 버전은 기존 규칙대로 읽기 전용으로 남는다.

### D-210 modifier는 0단계 기존 `targetScope`를 재사용 · 확정 (사용자) · 기획안과의 차이
- 0단계 `targetScope`(연령대 · 성별 · 가구 · 생애단계 · 메모)를 6-B Persona 이름 · Desire 초안 프롬프트의 힌트로만 넣는다. 클러스터링 입력에는 넣지 않는다.
- 위험과 막는 방법: 같은 값을 8-D 스코프 대조에도 쓰므로, 생성에 섞이면 "선언 밖 → FUTURE" 판정이 흐려질 수 있다. 그래서 힌트는 6-B 초안에만 넣는다(사람이 확정). 8-A CCM · 8-C 속성 생성 프롬프트에는 넣지 않는다(기획안 8-D 원칙 유지). 6-B 화면에 "초안 힌트: 0단계 대상 선언" 표시.
- 기획안과의 차이: 새 `modifier` 필드를 만들지 않는다.

## 설계 (2026-10-02, Claude 제안 — 02-design.md 13절)

### D-211 미결 산식 · 튜닝값은 params 모듈 + 결과 JSON 기록 + 화면 "잠정" 배지 · 제안
- Opportunity(I + max(I − S, 0)) · Persona 집계(문서 수 가중 평균) · L3 k(C_v 최대, 2~4) · centrality 정규화(최댓값 1) · DPP σ 0.3 · w_r 0.3 · combo_rarity 임계 · novelty 임계(high) · Traceable 0.5 · emerging · lexical_surprise 정의.
### D-212 Known Insight 판정 캐시는 (문서, 항목) 단위 · 제안
- 문장 추가 → 그 항목만 캐시 문서 재판정. 넘긴 원문 추가 → LLM 없이 새 발견 탭만 재계산.
### D-213 인용은 원문 기준 · 미확인이면 등급 하향 · 제안
- `quote{field: title|body|comment, idx, start, end}`. 벡터용 2,000자 자르기 전 원문에서 공백 정규화 후 정확 일치.
### D-214 LDA Context 센트로이드 = 배정 문서 Voyage 벡터 평균 · 제안
- `dist_centroid` · 밴드(Context 안 P50/P90) · 8-E 레이더가 공유. 문서는 θ 최대 토픽에 하드 배정.
### D-215 dims 자유 문구 코드화(임베딩 코사인 ≥ 0.85 탐욕 묶음) 후 조합 빈도 · 제안
### D-216 `author_count` = 문서 작성자 중복 제거(댓글 작성자 제외) · 제안
### D-217 확정 인사이트는 다음 세션 Known Insight 서랍에 "이전 세션 추천"으로만 · 제안
### D-218 군집 구조를 넣은 합성 픽스처로 결정적 테스트 · 제안
### D-219 사이드바 클러스터링 · 근거 탐색 · 페르소나 · 인사이트 / "임베딩" 표시 제거 / 6 · 7 · 8단계부터 다시 · 제안
### D-220 L2 문서 배정 = 겹치는 어휘 centrality 합 최대 공동체, 없으면 가장 큰 Persona · 제안

## 디자인 리뷰 (plan-design-review, 2026-10-02, 모두 사용자 개별 승인)

### D-222 페르소나 화면은 "전체 맵 | Persona 카드" 두 보기 · 확정 (리뷰 1A)
- 들어오면 세션 전체 Opportunity Map이 먼저 보이고, 점을 누르면 그 Persona 카드로 간다. 카드 안에는 맵 탭이 없다(구역 · 기회 값은 CCM 행).
### D-223 근거 탐색 실행 중 끝난 Context부터 열람 · Known Insight 추가 가능 · 확정 (리뷰 2A)
- 행 상태 배지(완료 · 진행 중 · 대기 · 실패). 완료된 Context는 Known Insight가 바뀌면 "새 발견 다시 계산" 버튼. "페르소나 만들기"는 전부 끝날 때까지 잠금.
### D-224 6-C는 Persona 단위 "Context 모두 확정" + 개별 확정 · 확정 (리뷰 3A)
- 반례 · 문서 부족 포함 시 경고. 세션 전체 일괄 확정은 없음.
### D-225 전체 맵 표기: 클러스터 = 점 모양, Persona = 명도, 선택만 파랑 · 확정 (리뷰 4A)
- Person A 색(파랑 하나 + 회색)을 유지하고 색만으로 구분하지 않는다.
### D-226 전체 맵 아래 정렬 가능한 Context 표(키보드 · 낭독기 대체, 표↔점 서로 강조) · 확정 (리뷰 5A)
### D-227 7 · 8 화면의 Persona 선택은 왼쪽 목록(클러스터별 묶음 · FUTURE · 상태 배지) · 확정 (리뷰 6A)
